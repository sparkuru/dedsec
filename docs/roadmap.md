# 仓库路线图

## 目标

将仓库建设为两条相互支撑、互不污染的主线：

- 研究线：形成有源码锚点、可复现、能解释边界的 LSPosed-like 知识库。
- 发布线：形成可独立构建、验证、授权和发版的自研工具集合。

研究不是发布项目的运行时依赖。实验验证成熟后，以最小实现进入具体项目。

## 阶段 1：Foundation

建立目录语义、证据规则、学习路径和项目发布契约。

完成条件：

- 顶层 README 能说明仓库用途和入口。
- 框架地图区分 Zygisk、APK patch、Riru 和虚拟化路线。
- 学习路径为每个阶段定义可观察的验收证据。
- `projects/`、`labs/` 与本地上游源码具有明确边界。
- 未跟踪的 `src/` 内容未被无审查搬运。

## 阶段 2：Mechanism Labs

建立自编 target app，并依次完成 legacy Xposed API、libxposed API、ClassLoader/DexKit 和模块通信实验。

完成条件：

- 每个实验能从干净环境独立构建。
- 实验记录包含预期、步骤、观察、失败现象和结论。
- 能用日志或测试证明包、进程、类加载器和 Hook 时机。
- 同一个目标至少分别由 legacy API 和 libxposed API 实现一次。

## 阶段 3：First Product

选择一个范围窄、结果可验证的工具作为首个产品。默认候选为 QQ 图片提取器。

完成条件：

- 项目不依赖 `labs/` 或 `workbench/`。
- 宿主适配层与业务层隔离。
- 支持范围精确到宿主版本和 Android 环境。
- 适配失败时 fail closed，并提供可诊断结果。
- 发布包、源码 tag、CHANGELOG 和兼容报告能够对应。

## 阶段 4：Release Platform

为多个工具建立统一但不强耦合的质量和发布规则。

完成条件：

- CI 按项目路径选择构建任务。
- tag 使用 `<project>/v<version>`。
- 每个 release 记录 commit、依赖版本、宿主兼容矩阵和校验和。
- 第三方来源和许可证检查成为发布门。
- 至少两个项目能够独立发布，且不共享宿主私有适配代码。

## 优先级

1. 建立 target app 和第一个最小 Hook。
2. 完成 Vector/libxposed 加载链追踪。
3. 建立版本化 resolver 实验。
4. 将 QQ 图片提取器调研转化为可运行的最小纵切。
5. 审查 `src/mikufans`，决定其中哪些是项目、实验或本地参考材料。
6. 首个项目可构建后再引入 CI 和自动发版。

## 暂不处理

- 自研 LSPosed/Vector 框架替代品。
- 全设备、全 ROM、全宿主版本兼容承诺。
- 以隐藏 root、框架或模块为主要目标的功能。
- 未经逐文件许可证确认的上游代码搬运。
