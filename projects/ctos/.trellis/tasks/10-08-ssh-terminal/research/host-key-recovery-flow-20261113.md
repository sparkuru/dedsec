# Research: changed-host recovery and trust-source ownership

- Query: Identify the existing changed-host evidence, actual config trust source, and safe ways to reduce the current repeated recovery interactions after the user's successful config/private-key test.
- Scope: internal, static source/spec inspection only; no board, real configuration, account, or private-key access.
- Date: 2026-11-13

## Findings

### Existing visible flow and why the source choice appears

`password_connect_page.dart:903–945` presents a changed-host dialog only after the failed attempt has settled. Recovery at `:948–1020` clears transient UI secrets and reloads the form after the protected route. Direct password or standalone keyboard authentication chooses the password group, and a manually targeted key chooses the config group. For any config alias the UI intentionally sets `selectGroupForForget` instead of inferring a source from the selected authentication method (`:978–995`).

The screenshot's duplicated rows are two distinct managed objects, even when they contain the same fingerprint: `SshHostTrustManagement.java:16–35` binds `ssh/known_hosts` and `.ssh/known_hosts` to different exact file IDs and identities. `host_trust_page.dart:806–895` prints each group, path, each record and an action; a fresh preview then repeats metadata in a second confirmation (`:520–579`); the committed success and uncertain result have a distinct button-bound receipt (`:664–715,719–759`). `SshProfilesBridge.java:361–427` likewise separates non-authorizing query from independently prepared proposal. Equal host/fingerprint values in two groups do not prove which source rejected this connection; removing both or selecting the first is not justified.

For config connections, however, the backend does have the **actual** source before the KEX starts. `ssh_config_eval.c:964–1012` takes the actual evaluated Options and resolves each effective `UserKnownHostsFile`; `SshConnectionMaterial.java:285–296` selects exactly one existing typed known-hosts object or rejects missing/multiple sources. Config-password stores `trustPath` at `SshPasswordConnector.java:444–467`, config-key at `:494–539`, and config-keyboard at `:543–564`. The final `hostsPath`, `hostsId`, `hostsIdentity`, actual host/port, role and snapshot are then bound for `snapshotFor` and `openManaged` at `:273–330`. Current manifest shape admits only the supported managed objects (`SshConnectionMaterial.java:121–151`), while a future compatible implementation should not assume every future valid source maps to a current two-value enum. The host-trust management API itself currently accepts only those two fixed enum groups, not arbitrary caller paths (`SshHostTrustManagement.java:16–35,84–98`).

The existing failure event is `state` plus a string reason; `SshPasswordConnectBridge.java:430–456` does not send the actual source. Safely streamlining config recovery therefore needs a host-derived typed fact or opaque original-attempt-bound receipt carrying the actual target/source identity, or a protected re-evaluation of alias/binding/current config with exact target/source comparison. A Dart guess or user-supplied path alone must not authorize a different deletion. Handle changed config, source replacement, epoch/revision or endpoint changes as stale, not by silently falling back to the default group.

### CHANGED offered key and signed KEX

During `ssh_hostfile_issuer.c:263–285,319–342`, the issuer has the actual offered key, its canonical SHA-256 fingerprint, classification, and base digest. For CHANGED it returns without preparing or handing off a replacement (`:344–349`). `ssh_native_client.c:667–688` records only a CHANGED/REVOKED/CERTIFICATE rejection enum and stops before the host-evidence callback. `:725–730` wipes the issue and releases the offered key/fingerprint. The later getter exposes just the enum with owner, role, deadline and view checks (`:2354–2375`); JNI `ssh_session_jni.c:342–357` and Java `SshNativeSession.java:698–704` turn that into the typed code. The existing failed-attempt interface cannot display the new fingerprint or continue the failed transport.

The callback occurs **before** cryptographic server signature verification: generated pinned `kexgen.c:163–175` invokes `kex_verify_host_key`, and only `:222–240` later verifies the KEX signature and invokes the patched `ctos_ssh_kex_signed`. The fixed upstream patch is `android/ssh/openssh-10.6p1-kex-guard.patch:34–45,60–69`. An offered fingerprint at the existing callback is useful for explicit out-of-band comparison but is not already a signed KEX proof. Do not label it verified, turn it into a pre-approved retry, or treat an arbitrary Dart fingerprint as authority.

### Existing NEW review, persistence and secrets

The existing NEW flow already asks for approval **before** KEX signature verification. The issuer generates an exact replacement and hands it off only for NEW (`ssh_hostfile_issuer.c:349–401`); `SshNativeCallbackAdapter.java:384–405,520–533` obtains a candidate, calls the authority/review mailbox, then performs the managed write-back in the same callback. `SshHostKeyAuthority.java:172–187` accepts an approved, exact NEW proposal and rejects CHANGED; `SshHostKeyReviewMailbox.java:6–8,90–143` permits one exact NEW review, a maximum 30-second wall wait, current role/deadline checks and explicit decision. `SshManagedKnownHostsProvider.java:475–515` persists the once-only exact CAS **before returning from that callback**, hence before KEX signature/NEWKEYS. Its post-write failure path reports uncertain and fails closed (`:516–528`). A later signature failure must not be described as proof that this already committed trust write rolled back.

Credentials are a separate gate. KEX is completed before userauth begins (`SshPasswordConnector.java:328–336`), and the selected-secret callback requires matching host proof **and** signed KEX/NEWKEYS evidence (`SshNativeCallbackAdapter.java:675–688,750–764`). Flutter clears input controllers immediately after submission (`password_connect_page.dart:1145–1146`), but within the **still-live original attempt** the connector owns bounded transient password/key material or selected saved-credential authority (`SshPasswordConnector.java:79–96,108–126,610–627`), and cancels/wipes it on attempt cancellation and retirement (`:185–195,670–683`). Thus an intentionally designed CHANGED review *inside that same live attempt* can in principle avoid asking for the one-time secret again, without retaining it after a failed connection. The present CHANGED path, however, ends the attempt and cannot simply be revived.

This statement is specifically about the production selected-credential callback and sending authentication material to the SSH session. It is **not** a guarantee that all local secret access waits for KEX: `prepareKeyPhrase` reads a selected saved phrase and locally checks the encrypted key before opening the transport, and an explicitly requested phrase save can commit at `SshPasswordConnector.java:570–627`; explicit config-password save can also commit before KEX at `:420–440`. These existing distinct effects need their own accurate receipt/lifetime treatment.

### Proposed provisional KEX followed by source-bound commit

The parent asked whether CHANGED could display the actual offered key, obtain one explicit user decision, temporarily admit **only that key** to KEX, validate its signature/NEWKEYS, commit the exact changed trust source, and only then release credentials.

**Established by static source, reusable only with new contracts:**

- Native currently has a one-time pending-host pin at `ssh_kex_guard.c:89–108`; `:124–155` requires the same fingerprint through native approved → signed → complete → ready. `ssh_native_client.c:695–710` pins the exact offered key in the current role and `:2315–2318,738–767` calls the KEX-completion callback only when KEX has finished, inbound NEWKEYS is installed, and the queued output is drained. These checks provide useful ingredients; their current semantics still assume an already approved managed-host result.
- The native completion callback runs on the session's callback owner and receives cycle/session digest; its native `ctos_ssh_kex_ready` gate checks the role, hop, nonce, connection binding, original deadline, pinned key and signed/completed state. A newly defined limited completion fact must also remain tied to the original provisional decision and exact offered key; the current Java callback arguments do not independently carry all of those fields.
- The existing exact trust writer checks proposal, role, snapshot, object, source digest, ciphertext, epoch, validator, revision, foreground and deadline before and during effect (`SshVaultAdapter.java:174–232`, `AppSecrets.java:1975–2003,2042–2055,2126–2208`). Its own successful trust write can retain only the exact role-owned public view while advancing the session epoch once (`AppSecrets.java:2184–2198`, `VaultSession.java:92–99`). This is a relevant mechanism, not proof that a moved-after-KEX implementation already works.
- Effective config hostfile list is retained by native, but production `singleTrustPath` accepts exactly one **existing** managed KNOWN_HOSTS object; missing configured entries are skipped, two existing ones are rejected, and none gives a dependency error (`SshConnectionMaterial.java:285–296`; `SshDirectConfigPlanTest.java:240–263`). Thus the current connector does not merge multiple live sources.

**Dependency cycle that requires implementation, not just reordered calls:**

1. The existing native host result requires `CAS_COMMITTED` for NEW before pinning the key (`ssh_native_client.c:548–580`). Java publishes `hostProof` only after `verifyHost` has completed the NEW write (`SshNativeCallbackAdapter.java:384–405,520–533` and `:349–353`). CHANGED currently never reaches this path.
2. `onNativeKexComplete` currently requires that already-published `hostProof` before creating `SshKexProof` (`SshNativeCallbackAdapter.java:554–564`); `SshKexProof.java:29–44` accepts only KNOWN/NEW. The exact trust writer also requires a formal host proof and NEW classification (`SshVaultAdapter.java:217–232`). Simply waiting for existing KEX proof before writing therefore deadlocks or fails closed.
3. Break the cycle with a **distinct, non-credential-capable provisional approval and signed-KEX fact**, not a fake normal host proof or an early normal `kexProof`. The proposed control flow is: construct and bind an exact candidate plus old/new display facts; user explicitly authorizes the still-unverified offered fingerprint; a distinct typed native result allows only that exact key's KEX; after native signed/complete/ready checks, match role, cycle, session digest, offered key, source snapshot and pending decision; run the one-shot atomic source-bound CAS; only on confirmed success publish normal host/KEX authority and permit userauth. Cancellation, signature failure or staleness before commit drops the candidate without write; a write whose final result cannot be delivered is uncertain, locks/blocks continuation and must never be auto-retried.
4. Candidate ownership must survive the first callback: the existing `onNativeHostEvidence` `finally` closes the managed proposal at `SshNativeCallbackAdapter.java:419–420`; candidate/provider/snapshot and any review receipt need an explicit exclusive pending owner across callbacks, with bounded lifetime, one-shot promotion, and cleanup on close, cancellation, bad signature, timeout or error. Existing callback reentrancy guards, main-thread decision delivery, and vault/session lock order need an explicit audit; do not assume a synchronous commit from the post-KEX callback can safely reenter all existing paths.

**Still requires real protocol/design probes:**

- Exact provisional JNI/wire/type and callback ordering; KEX completion cannot publish normal credential-granting proof ahead of CAS, including on stale/duplicate callbacks or fake cycle/digest.
- Run an actual signed SSH peer through KEX on the **same socket**, pause the owned candidate until signature/NEWKEYS, commit in the session-owner path, then exercise normal password, unencrypted/encrypted selected key and KBI continuation; separately prove bad signature, cancelled/expired review and peer disconnect cause zero trust writes and zero selected-credential callback deliveries.
- Prove exact own-CAS epoch advance after NEWKEYS keeps the original native public-view borrow, transient/saved credential guards, role and session digest live; independently prove unrelated mutation or changed source before the write invalidates the provisional candidate. Existing NEW writes before KEX are not this test.
- Probe both the 30-second mailbox ceiling and original 60-second role deadline, as well as the potentially shorter `transportDeadline` calculated from actual `ConnectTimeout` (`SshPasswordConnector.java:328–332,460–465,510–514`); the current callback can wait inside one native step, so no inference about priority or peer availability is justified without execution.
- `ctos_ssh_host_trust_inspect` (`ssh_host_trust.h:16–27`) is a supplied-body management projection, not a live-role mutation authority. Reuse its precise parser/byte-span/blocking policy only by providing independently validated original role/source/key bindings and a new candidate contract. Its omission of all matching ordinary rows must be shown accurately in the confirmation; appending the new offered key must keep limits and unrelated bytes intact.

### Design choices and boundaries

1. **Narrower UI-only improvement:** keep CHANGED as a failed connection and the existing two trust transactions. Put a source selection, exact fresh preview and its explicit confirmation in one compact coherent route; avoid repeating line/source details in multiple screens. When the actual source is not established, preserve an explicit choice and expose distinguishable source details. For direct targets, the current `_autoForgetGroup` mechanism already queries and prepares the known group (`host_trust_page.dart:465–516`). A fresh query is still not the commit authority: use the prepared ticket/binding. A success receipt can potentially make its actual acknowledgement button mean “继续连接”, provided the lifecycle contract is consciously updated and uncertain outcomes still require explicit, retained recovery. A new connection must run the real NEW-key review and may need a password or encrypted-key passphrase again.
2. **True one-confirmation replacement on the same live connection:** extend the native issuer to construct a bounded replacement from this exact source snapshot, preserving unrelated bytes and blocking shared, revoked, CA, unsupported, malformed and other non-removable rows; bind the offered actual key, exact old records, old/new body digests, role/hop/endpoint, object ID/path/identity, request/deadline and current vault state into a distinct CHANGED review and one-shot CAS. Extend the existing NEW-only candidate handoff, Java evidence/proposal/authority/mailbox and native proof matching rather than accepting caller text or using the idle-only independent forget API. The app can then show old and offered new fingerprint together, obtain one explicit decision, commit only that candidate and continue the same KEX, which must still verify the signature and reach NEWKEYS before any credential read. This is a cross-layer trust policy change, not a button-only refactor. Existing NEW pre-signature write behavior cannot be silently assumed acceptable for replacement; decide and test what a failed signature or interrupted post-write delivery means. A provisional, non-credential-capable KEX that verifies the signature before persistent replacement is another design, but changes the current KEX guard/state machine further and needs its own proof.

The independent forget path blocks concurrent connect and active services (`SshProfilesBridge.java:352–359,395–427,641–705`); its 120-second source-bound ticket/preview cannot be injected into the active connection. It uses actual parser matching and exact byte-span replacement, blocks shared/marker/unsupported rows, and preserves unrelated entries; see `ssh_host_trust.c` and the host-trust spec. All mutations must retain one-shot commit, lifecycle/lock/background/revision/deadline guards, uncertain-after-write handling and truthful receipts. A reconnect/continuation must remain a new explicit intent, not silently replay a password, answer, passphrase, old decision, or stale config/key selection. Existing key-only reconnect-on-open logic (`password_connect_page.dart:201–205,310–396`) permits only a fresh guarded, unencrypted-key path; it is not a general password or changed-host retry.

## Tests to retain or extend

- False CHANGED diagnostics, genuine CHANGED and REVOKED/CERTIFICATE/invalid, no wrong recovery, late connected, target/config/source change, stale generation, duplicate/forged decision, back/route coverage/background/lock/timeout/cancel.
- Exact default and alternate config source, same fingerprint in both groups, missing/multiple sources; only the actual selected object can be modified and stale source/binding blocks commit.
- Fresh preview content differs from earlier query, source mutation before commit, one-shot/replay, unrelated bytes, hashes/CRLF/no-final-newline, shared selectors and CA/revocation/unsupported rows, cancellation before/after write and uncertain delivery.
- If same-attempt replacement is implemented: actual native peers covering CHANGED offered key, false signature, altered key after decision, same session/role/KEX, zero selected-secret reads before signed NEWKEYS, no fallback or password replay after failure, 30-second/original role/shorter transport deadlines; Java/JNI one-shot candidate/CAS and Flutter exact user-confirmation and touch/large-text handling. Compile/mock tests do not replace real protocol/device validation.

## Caveats / Not Found

- This is static inspection, with no attempt to observe the user's device or reproduce an installed-app session. User confirmation establishes only the reported config/private-key experience.
- No existing production API was found that exports a CHANGED offered fingerprint or authoritative failed-attempt trust-source receipt to Flutter. A claim that a single current button can safely approve the new key and resume the same connection would require new native and host contracts.
- Exact valid alternate config paths beyond current managed shape and all corner-case ordering during short `ConnectTimeout` need dedicated implementation tests; do not assume they work merely because the plan stores a path.
