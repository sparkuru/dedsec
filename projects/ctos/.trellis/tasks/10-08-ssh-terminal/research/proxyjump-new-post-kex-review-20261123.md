# Research: ProxyJump NEW review after provisional signed KEX

- Query: Can a non-authenticating provisional NEW handshake finish before user review, while the owner pumps the parent and relay? How must the displayed fingerprint, ticket and later trust write be bound?
- Scope: internal source and pinned upstream source; design and security review; no implementation or tests run.
- Date: 2026-11-23

## Findings

### Assessment and contracts

The proposed order is technically plausible for the existing **hop-1 child** milestone, but is not implemented as a product flow. For `NEW` and `StrictHostKeyChecking=ask`, the client can temporarily pin the actually offered key solely to complete a signed KEX, with no host proof, CAS, userauth, credential or shell. It can then present the fingerprint outside JNI, pump while waiting, and require explicit acceptance plus separate exact write admission. A valid signature proves possession of the offered key, not that it belongs to the intended host; the user must independently compare the fingerprint. The target can observe and log the transport/KEX before acceptance; the known jump may already have received its separately confirmed credential, but the target credential must not be used.

Ordinary MANAGED mode requires approved, `CAS_COMMITTED` NEW before pinning (`.trellis/spec/backend/ssh-native.md:439-446,474-476,3819-3822`). The native-only child contract supplies a separate non-authorizing signed milestone (`.trellis/spec/backend/ssh-proxyjump-child.md:124-170`), but production JNI does not register its hooks. Productizing the exception requires an explicit spec change while preserving ordinary direct behavior. The current draft places user review before provisional pin (`design/ssh-proxyjump.md:25-35`) and must be updated if this order is selected. The task requires actual endpoint/fingerprint and explicit acceptance before trust/credentials (`.trellis/tasks/10-08-ssh-terminal/prd.md:382-385`); preserve the separate CHANGED contract's review-then-signature-then-CAS order (`.trellis/spec/backend/ssh-host-trust-management.md:244-249,301-316`).

Enforce the effective hop policy independently before provisional pin: current `StrictHostKeyChecking=yes` rejection lives in the ordinary `UnknownKeyIssuer` (`SshPasswordConnector.java:1089-1097`), which the provisional branch bypasses. `yes` must reject NEW without prompting; unsupported `no`, `off`, and `accept-new` stay unsupported. KNOWN, CHANGED, REVOKED, CERTIFICATE and INVALID must retain their own paths.

### Source evidence and fingerprint binding

- `android/app/src/main/cpp/ssh_native_client.c:1204-1292,1358-1368` clones the actual offered host key, calculates raw SHA-256, classifies it using the real managed hostfile, hands off its NEW candidate, then temporarily pins the same key. The callback named `provisional_new_review` is an internal staged acknowledgement, not human approval. `android/app/src/main/cpp/ssh_hostfile_issuer.c:274-277` derives the canonical display fingerprint from that actual `host_key`.
- Pinned OpenSSH source `build/ssh-route-host-jni-20261120/openssh-10.6p1/kexgen.c:160-172,217-234` parses the host-key blob, includes it in exchange hash H, then verifies the signature using the same key. `android/ssh/openssh-10.6p1-kex-guard.patch:13-21,35-41,60-69,83-92` invokes the signed guard only after verification; `android/app/src/main/cpp/ssh_kex_guard.c:46-52,91-106,123-154` binds the guard to that pinned key fingerprint and requires the approved and signed keys to match. The guard's `approved` flag is not persistent trust.
- `android/app/src/main/cpp/ssh_native_client.c:1396-1432,4343-4402` records a cycle plus SHA-256 of the SSH session ID after guarded KEX. Ordinary `completed` remains false. `ctos_ssh_native_client_provisional_new_ready` samples signed KEX, owner/role/view/parent liveness and current outbound drain; it is neither a host proof nor atomic CAS admission.
- `android/app/src/main/cpp/ssh_callback_jni.c:969-980,1012-1017` and `android/app/src/main/java/im/majo/ctos/SshNativeCallbackAdapter.java:158-187,752-786,820-845,862-880,896-939` contain a test-hook-only JNI bridge and pending fixture. The fixture binds `Evidence`, source, exact candidate object and ID, callback serials, KEX cycle and session digest; its checks are samples, not atomic ordering against candidate consumption or revocation.
- `android/app/src/main/java/im/majo/ctos/SshHostKeyAuthority.java:24-57,73-109,165-200,270-283` shows that the existing review binding covers role/endpoint/key/base/replacement, but not the candidate object, source revision or signed KEX cycle/session. `Proof.permitsCredentials()` permits NEW, so a `Proof` must never represent provisional state. `SshManagedKnownHostsProvider.java:56-99,122-132,200-252,549-560,685-732` retains the source object/path/epoch/revision, candidate identity and body, and consumes the candidate under its provider monitor.

For UI, create an immutable, owner-bound, non-authorizing signed-candidate state from the native `Evidence` **after** the same candidate's guarded KEX and outbound drain. Bind the role instance/nonce/connection, hop and endpoint, native child/callback, source path/object/view/epoch/revision, candidate ID and object, key type/fingerprint, base/replacement digests, KEX cycle and session digest. Derive the ticket and displayed fingerprint from that state, never from UI-returned key/path/body. A user decision authorizes only this ticket's exact candidate; it is not a host or KEX proof.

### Owner, mailbox and locks

`SshPasswordMailbox.await` polls outside its monitor and takes the monitor only for short response transfer/wait (`android/app/src/main/java/im/majo/ctos/SshPasswordMailbox.java:81-137`). `SshHostKeyReviewMailbox.awaitDecision` currently has no owner poll (`SshHostKeyReviewMailbox.java:89-188`), though its one-shot ticket, independent `resolve`/`cancel`, live checks, 30-second ceiling and nonblocking sink are reusable (`:18-86,190-242`). Extend or parallel this wait for a ticket issued only from the signed pending candidate. The owner must leave `SshNativeSession.step()` and JNI's global `sessions_lock` (`android/app/src/main/cpp/ssh_session_jni.c:182-201,692-720`) **before** publishing or waiting. Run every parent/relay poll and sink call outside the mailbox monitor; do not hold callback/session locks or a native wire-effect permit across UI or vault I/O.

`SshPasswordConnector.java:1137-1209` shows the ancestor `jumpStatus`, `step`, relay pump and cancellation pattern. Add a separate provisional branch to `stepJumpChain`/the KEX loop (`:985-1045`): signed provisional state is not `StepResult.complete`, and another child `ctos_ssh_native_client_step` in state 2 returns `EALREADY` (`ssh_native_client.c:4101-4113`). Expose a narrow owner-thread JNI pending status and pump the parent/relay until the signed output is drained. Do not call `pollSelectedPasswordPrompt`; it requires selected authentication and `SERVICE_READY` (`SshNativeSession.java:1631-1653`).

Register/clear the connector's existing one-shot `mailbox` and `ticket` as in `SshPasswordConnector.java:693-714`; preserve its `decide` ID + binding + exact ticket checks (`:579-596`) and validate the new deadline/policy in `hostKeyPending`. `SshPasswordConnectBridge.java:525-578` publishes public fields and checks pending only at a point in time, so cancellation can race publication; recheck after the decision. The existing Flutter dialog shows the received endpoint/type/fingerprint and asks the user to compare (`lib/ssh/password_connect_page.dart:1855-1903,3386-3405`).

After approval, pump and revalidate the exact signed pending state and obtain a **separate one-shot write admission**, ordered against candidate consumption, source revision change, generation revocation, cancellation and expiry. `ready` and repeated sampled candidate checks do not provide that ordering. Release a native wire permit before terminal cleanup or callback lifecycle locks (`ssh_native_client.c:4384-4396`); never perform vault I/O under the short wire permit. Preserve confirmed/failed/uncertain write outcomes (`.trellis/spec/backend/ssh-trust-commit-ack.md:19-25,38-50`). Only a confirmed write permits cleanup of the old chain followed by a fresh config/vault read and new roles/generation. The current Flutter review ordering rejects decreasing hop numbers (`password_connect_page.dart:1881-1883`), so restarting inside one request needs an explicit attempt identity and a completed old-owner cleanup (`design/ssh-proxyjump.md:27-37`).

### Unresolved liveness and deadline boundaries

Pumping only parent and relay can put incoming ciphertext in the child socket without parsing that child's SSH DISCONNECT, EOF, rekey or unexpected packets. The ordinary child step is unavailable in provisional state 2; the current `ready` checks observed parent/relay and outbound drain, not all incoming child traffic. A narrowly bounded, non-authenticating provisional poll must define how it processes or rejects encrypted packets and EOF, handles backpressure/bounded memory, and prevents service requests, authentication, secret release, rekey and candidate replacement. Even such a poll cannot prove there is no network close in flight: admission can only order observed liveness and local revocation, not promise future remote liveness.

Per-hop `ConnectTimeout` remains active in Java before normal KEX completion (`SshPasswordConnector.java:985-989,1037-1044`) and in the native wire permit (`ssh_native_client.c:424-437,493-514`). `provisional_new_ready` still acquires this permit. Thus a two-second hop deadline can expire while a user reviews; flipping only Java's `jumpTransportActive` would not change the native deadline. Choose either to bound review by the current short hop deadline or explicitly design a post-signed/drained review phase that retires only the connection deadline while retaining request/role deadline, UI ceiling, effect generation and revocation checks. Do not silently extend role/request deadlines.

### Tests needed

- Real JNI/Java and encrypted vault: delayed review with parent/relay progress; exact displayed offered fingerprint and candidate/source/cycle binding; no `Proof`, CAS, target credential or shell before acceptance/admission; confirmed write followed by complete cleanup and fresh route. Reject, cancel, no UI, stale/cross-hop/replayed ticket, altered candidate/source/revision/fingerprint, timeout and late acknowledgement.
- Encrypted peers: valid/bad signatures, wrong key, malformed packet, observed parent FIN/close, child EOF/SSH DISCONNECT during review, backpressure, keepalive/EXT_INFO, rekey, bounded buffers and output drain. Verify state, cleanup and no authentication. Test cancellation/lock/expiry around exact admission, CAS uncertainty and retryable candidate abort.
- `StrictHostKeyChecking=yes` denies before provisional admission, `ask` prompts, all other classifications retain behavior. Exercise the selected hop deadline policy, UI hop/attempt ordering, no reentrant JNI/mailbox lock inversion, and owner/service cleanup before restart. Separate synthetic, native/JNI, Docker server, Android/device and manual UX evidence.

## Caveats / Not Found

- Existing provisional scope covers only hop 1 under a root parent; it does not solve a NEW root jump or deeper chain. The current product route refuses first trust.
- A safe atomic write admission, post-KEX non-authenticating child poll, and production registration of these hooks were not found. Source may change concurrently; the findings are from 2026-11-23 and no tests were run.
