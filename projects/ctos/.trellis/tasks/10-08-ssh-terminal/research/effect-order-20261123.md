# Research: Ordering ProxyJump trust and credential effects

- Query: What exact production operations and invalidators must be ordered to safely enable one-hop child trust and authentication, and what can be implemented first without claiming full ProxyJump support?
- Scope: Internal source and project specifications only. No device, real account, external server, network, execution, or code changes.
- Date: 2026-11-23

## Current observations

1. `ssh_session_jni.c:182-201,678-705` takes the nonrecursive process-wide session-table mutex before stepping the client and holds it across synchronous Java callbacks. Ordinary session JNI or Java `enterNative` reentry from the callback is therefore not a valid ancestor check. The private receiver-bound check at `ssh_callback_jni.c:805-809` reaches `ssh_callback_adapter.c:749-805` and native client TLS scope at `ssh_native_client.c:248-273`: it checks the exact target, thread, active callback and real ancestor chain, then returns a **point-in-time** result. It deliberately releases `callbacks_lock` during traversal and cannot bind a later effect to that result.
2. The callback scope's `upstream_proof` at `ssh_native_client.c:223-238` explicitly accepts an ancestor shell in `RUNNING` **or `CLOSED`**. Retained downstream proof at `:2347-2381` likewise permits CLOSED when `require_open=0`. This permits already received output to drain; the proof does not check ancestor `remote_eof`, `local_eof`, `remote_close` or relay half-closes. It must not be reused as authorization for a new trust commit, credential handoff or KBI response. An effect-specific traversal should check the exact chain's observed channel/relay state conservatively. A zero SSH window is backpressure, and even an apparently open channel cannot prove future network delivery.
3. Native transport and relay processing are owner-thread constrained (`ssh_native_client.c:199-220,223-238`), but a callback can be cancelled independently under `callbacks_lock` (`ssh_callback_adapter.c:699-705`), native roles under `roles_lock` (`ssh_role_bootstrap.c:262-278`) and native view handles under `handles_lock` (`ssh_view_handle.c:204-218`). Java cancellation is independently recorded in `SshNativeSession.java:1125-1132`, `SshNativeCallbackAdapter.java:1328-1340`, `SshPasswordConnector.java:472-495` and `SshSessionOwner.java:296-313`. Vault locking holds the session monitor while revoking its exact lease (`VaultSession.java:68-74`); the shared Java view also exposes a cancellation path (`SshSharedPublicView.java:66-70`). An effect guard that only watches one of these cannot establish chain ordering.
4. Selected credential reads enter the actual Java receiver through `SshNativeCallbackAdapter.java:1254-1283`; its invocation guard currently holds the child callback `stateLock` during `publish`. Saved/private-key reads reach the final bounded receiver through `AppSecrets.java:2785-2814`, whose effective Java lock order is original callback guard → request/guard → `publicationLock` → vault `session` → operation → exact role/view → receiver. `SshCredentialBridge.java:237-264` intentionally supplies an `AppSecrets.SshRoleGuard`; a plain `AppSecrets.boundGuard` is not an `SshRoleGuard` (`AppSecrets.java:24-49`) and must not silently discard `withRole`. Transient passwords have a different final path at `AppSecrets.java:686-700`; transient keys have their own bounded bundle path.
5. Server-driven password input does **not** use the selected-secret callback. `SshPasswordConnector.java:1115-1118` checks, polls and calls `SshNativeSession.beginDiscoveredPassword`; `SshNativeSession.java:1532-1564` clones the input before JNI. `ssh_session_jni.c:887-909` copies the Java byte array to native memory **before** locking the session or validating native ancestry. `ssh_native_client.c:1456-1495` rechecks current auth proof but then `sshpkt_put_string`/`sshpkt_send` queues the password (`:1397-1413`); a failed later proof cannot undo that. KBI has the same two copies and independent packet path (`SshNativeSession.java:1900-1922`, `ssh_session_jni.c:983-997`, `ssh_native_client.c:1766-1807`). The native packet queue is not proof of network delivery.
6. The actual durable transition has a different shape: `AppSecrets.updateTrust` captures and encrypts a candidate, then calls the store (`AppSecrets.java:2163-2208`); `VaultStore.commit` writes/syncs, calls `guard.beforeCommit()`, and only afterwards calls `AtomicFile.finishWrite` (`VaultStore.java:46-81`). A cancellation can win between that check and the persistent switch. Existing `persisted`/native-ack tracking and `VAULT_COMMIT_UNCERTAIN` protect direct-connection outcomes but do not themselves serialize a child's write with all ancestor invalidations. `contentRevision` increments in `beforeCommit` (`AppSecrets.java:3355-3366`); the vault epoch advances after successful trust continuation (`:2185-2198`).
7. Fresh children deliberately fail NEW/CHANGED and all auth effects with `SSH_JUMP_EFFECT_GUARD` (`SshNativeCallbackAdapter.java:918-939`, `SshNativeSession.java:2328-2343`), and the product connector does not assemble a chain. This fence must remain until the selected effect and **all** its real invalidators are covered; `JumpAdmission` is an assembly capability, not an effect permit.

## Candidate design — not implemented

### Exact authority and invalidation

Build a chain-owned authority from actual owner-linked `JumpChildOwner` objects and the native clients/relays pinned by those owners; bind the private capability to connection, original view, each issued role, owner thread, exact child callback receiver and the current callback invocation serial. Native proof admission must originate inside the real native dispatch scope, not from Java-provided ancestor IDs, a reusable boolean or a public static constructor. For the first vertical slice, validate the existing receiver-bound native scope plus a **new effect-specific open-chain traversal** before entering vault metadata/role locks, while the original native session entry still holds `sessions_lock`. Native client/relay transitions on their owner thread cannot run concurrently with that callback; unobserved network closure remains an unavoidable observation limit.

The authority also needs one revocation/permit state shared with every out-of-band invalidation, including current/ancestor callback cancellation, Java `SshNativeSession.cancel`, the owner cancellation path, native callback cancellation, role closure/reclamation, exact Java/native view revocation, expiry/deadline and cleanup. The implementation must explicitly register the authority with those owners at assembly and pin its lifetime until all owners/permits retire. Merely adding a Java-side per-connection cancellation flag is insufficient if a native or role invalidator can still mutate outside it. Count and reject duplicate/foreign/replayed permits; a child cannot inherit another session's capability. No such shared state is present today.

One possible design to validate: a native-owned lock-free generation/cancel bit with short one-shot effect permits. Every external native/Java invalidator publishes cancellation or an incremented generation **before** its existing mutation; the final permit atomically verifies live generation, exact original deadline and no cancellation. The native dispatch proof binds the permit to the exact TLS invocation and receiver; it cannot be retained after that callback. This is a proposal requiring an explicit registration/lifetime design, not a demonstrated solution. Audit internal role/slot failure writes as well as named `cancel()` methods; marking only Java wrappers does not cover direct native revocation. `CLOCK_BOOTTIME` can expire without a mutator, so the final permit must check the original deadline, not only an invalidation bit. Define whether a bounded copy admitted just before expiry may finish after it; never describe an earlier time sample as continuous validity.

### Minimal vertical slice: real selected-credential receiver

Implement first for **a known-host child, selected saved password and its real Java/JNI native callback**, with encrypted `AppSecrets` plus in-memory store; keep product ProxyJump rejected and leave the fresh authentication fence closed for every path not covered. This slice should perform (a) actual callback-scoped native receiver/ancestor/open-chain proof, (b) exact Java role/view/selection/KEX and source checks, (c) final shared permit at the `AppSecrets.releaseSshSecret` bounded `receiver.receive` seam, and (d) a deterministic parent-cancel-versus-copy race. Compare wrong receiver/token/thread, immediate/deeper ancestor cancel, original deadline, role/view invalidation, replay and cleanup. Exercise actual production Java callback plus production JNI with an explicit synthetic peer and real encrypted vault; do not sum separate fixtures into one test. A test-only provider may supply fake host/key evidence only if labeled and it does not replace the actual callback/JNI path under study.

The lock order is decisive. **Do not hold a chain mutex or wait for revocation while entering vault `publicationLock`/`session`:** `VaultSession.lock()` already holds `session` while revoking, so outer chain lock → session and session → chain lock can deadlock. Preserve callback → publication → session → operation → role → view ordering. A possible final-point CAS inside the existing bounded receiver region must be nonblocking, take no native registry/session locks, perform no Java callback and use a previously authenticated, non-replayable TLS invocation capability. This would require an explicit, narrowly reviewed exception to `SshRoleContext.publishBound`'s present “no native calls” contract (`SshRoleContext.java:160-165`), or an equally demonstrable non-JNI mechanism. The existing receiver-bound scope function is **not** suitable at that point because it acquires callback/role/view locks. Implement all invalidation publication before using the permit; then prove lock order with actual concurrent tests. A one-shot precheck plus postcheck does not provide the guarantee.

For cancellation semantics, distinguish atomic **admission** from physical completion: if a short copy acquired the permit first, marking cancellation can reject every later permit while that already admitted copy is still finishing. If the contract instead requires `cancel()` to return only after every admitted copy finishes, drain outside vault/session/role/view/native registry monitors; never wait under a monitor needed by the copy. `VaultSession.lock` already serializes its body against a copy inside `session`, but other cancellation paths need their own proof. Decide this explicitly; elapsed time, an atomic flag or a best-effort wipe is not a drain.

### Follow-on paths before opening any product gate

- Add separate permits to the Java `owned` clone and the native JNI password/KBI input/packet transition. For JNI, first acquire the real session owner and verify the exact effect-open ancestor chain, then atomically admit and copy/queue under the bounded permit, wiping all Java/native buffers on every exit. Do not hold Java role/view/vault monitors across ordinary JNI: another native step holds `sessions_lock` while entering Java. If cancellation happens after the Java clone but before native admission, native must reject and the Java copy must be wiped. Verify whether `sshpkt_send` invokes any callbacks or can block before holding a permit across it; packet enqueue is not a network write.
- Add a durable-write-specific admission **at the final commit boundary before `finishWrite`**, recording an in-flight trust receipt before the store can switch. If cancellation wins before admission, no commit; if admission wins and cancellation/lock/role loss precedes confirmed native acknowledgement, stop further authority and preserve/lock on `VAULT_COMMIT_UNCERTAIN` whenever commit cannot be proven absent. Do not hold a chain/role/view monitor across encryption, fsync, `finishWrite` or user review. Admission and physical store completion are different events; a stricter “no disk switch after cancellation returns” promise requires a drain outside conflicting locks.
- Cover CHANGED and NEW, saved/transient keys and passwords, prompt responses, KBI, output publication, own-CAS fresh sources and revision provenance. Extend actual product factory from immutable effective route and exact vault revision; provide per-hop credentials, trusted UI routes, reverse cleanup and background ownership. Full-snapshot memlock cost and multi-hop capacity remain separate limitations.

## Suggested validation matrix

- Gate race barriers immediately before admission, after admission, inside bounded receiver, before JNI copy, before packet enqueue, before store `finishWrite`, after durable switch and before native KEX acknowledgement. Check both orders; cancellation/expiry/revoke winning first must prevent the applicable new effect, while an admitted durable write with uncertain completion must lock and report uncertainty.
- Use real JNI production session/callback tables and an encrypted synthetic SSH peer to test receiver/token/thread/invocation substitution and no `sessions_lock` reentry. Compare live chain, EOF/CLOSED/half-close, zero window, immediate-parent and deeper-ancestor cancellation. Assert buffers are wiped, no callback/FD/role/borrow leaks and cleanup is retryable.
- Separately run an isolated Docker OpenSSH one-hop test through the production Java/vault/JNI connection once the factory exists; distinguish test-owned accounts, host JVM, Android ART and background/device evidence. Test native and Java deadline clocks at the original deadline and retain direct-connection regression tests.
