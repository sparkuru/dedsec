# Research: ProxyJump NEW trust CAS, cancellation, and retry

- Query: After an exact child NEW candidate is approved and its same-key signed KEX completes, how can persistence be ordered with ancestor cancellation and how can the client safely offer another attempt?
- Scope: internal source and project contracts; design candidates, not an implemented protocol
- Date: 2026-11-23

## Findings

### Existing exact binding is useful but does not provide post-step NEW authority

The provider's `KnownHostsCandidate` binds the candidate ID, exact role/hop, endpoint, source object, snapshot, classification, key fingerprint and both digests; it clones the exact replacement and consumes it once (`SshManagedKnownHostsProvider.java:286-313`, `:316-375`, `:389-443`). `SshKnownHostsCandidateHandoff` consumes and wipes the Java input and aborts on failed transfer (`SshKnownHostsCandidateHandoff.java:31-77`). `proposalForExact` preserves the candidate's binding and exact source in `SshTrustProposal`, then closes the candidate (`SshManagedKnownHostsProvider.java:701-743`).

The existing NEW `SshVaultAdapter.trustRequest` / `updateTrust` and `VaultOperation.bindTrust` require a `SshHostKeyAuthority.Proof` (`SshVaultAdapter.java:197-244`, `VaultOperation.java:156-160`). NEW `Proof` is usable for credential authorization, so it must not represent a merely provisional pin. CHANGED's separate `ChangedAuthorization` is a useful exact-binding example, but `requireMatches` explicitly requires the original callback to remain in progress (`SshNativeCallbackAdapter.java:155-195`); it cannot be carried unmodified beyond the returned JNI step. A separate NEW, signed-only, once-consumable owner capability and a distinct operation binding are needed. Construct it only from the real exact child, callback, candidate and same signed KEX; the pending state must never produce an ordinary host/KEX credential proof.

`nativeCallbackAncestorProofsLive` is a point-in-time check available only within a real, unnested callback: native checks the owner thread, callback/client/role/environment, live borrow and actual ancestor proof (`ssh_native_client.c:262-314`; `ssh_callback_jni.c:884-888`). It is not a durable receipt for an after-step CAS. The intended new after-step capability needs a separately specified way to check the exact live native ancestry and order admission with revocation; ordinary session JNI must not be reentered from the callback holding `sessions_lock`.

### Current write and confirmation ordering

`captureSshTrust` serializes one work item, requires the exact context/proposal/one-shot operation, original revision and bound attached view, and clones the candidate bytes (`AppSecrets.java:2027-2084`). `updateTrust` checks authorization repeatedly, constructs a candidate only for the exact managed object and checks its current base digest (`AppSecrets.java:2184-2205`, `:2232-2254`). The store writes and fsyncs a temporary AtomicFile first, calls `guard.beforeCommit()`, then calls `finishWrite` and reads back (`VaultStore.java:46-81`). No filesystem write or candidate material should be performed while holding a short native effect permit.

The current short effect fence is a process-global atomic generation plus invalidator and active-effect counts (`ssh_role_bootstrap.c:26-35`, `:43-68`, `:87-130`). Invalidation increments the generation, blocks new effects and waits for already-admitted effects to drain. `SshSessionOwner.Cancellation.cancel()` holds its monitor during invalidation (`SshSessionOwner.java:41-47`); vault/session/view/role/callback invalidators can likewise hold their own locks before draining. **Lock-order consequence:** a permit holder must not then acquire one of those Java monitors. Otherwise an invalidator holding the monitor can wait for the permit while the permit holder waits for the monitor. Metadata/role checks, callbacks and any I/O cannot simply be placed inside the permit.

An implementation candidate is a dedicated exact-write admission whose linearization atomically validates the captured native generation and records an owner-visible one-shot write-in-flight receipt without taking invalidator-held locks. Only the bounded atomic admission would be inside the permit; release it before filesystem I/O. Cancellation before this admission denies the write. A cancellation, screen lock, role/view revocation, expiry or cleanup after admission but before safely confirmed completion must be recorded and lead to the existing uncertain/locked outcome if a durable write cannot be ruled out. The existing owner defers screen-lock/service rejection while `mayWriteTrust` and `creating` are true (`SshSessionOwner.java:127-151`, `:220-253`), but a new transaction must preserve that guarantee until its own completion; the current ledger is marked PENDING only after provider persistence (`SshPasswordConnector.java:483-505`; `SshManagedKnownHostsProvider.java:752-808`). The precise admission API, atomic state and lock ordering are not implemented or proven by this note.

There is a second race beyond owner Stop: all actual role/view/native invalidators, not merely the Java cancellation bit, must participate in the ordering. In particular `AppSecrets.commitEncoded` itself increments `contentRevision` and invalidates the effect generation in `beforeCommit` (`AppSecrets.java:3384-3395`), and `VaultSession.advanceTrustEpoch` invalidates it again (`VaultSession.java:98-106`). Other invalidators can interleave. Unconditionally re-snapshotting a new generation after the write, or treating `revision + 1` as proof that every relevant invalidation was the writer's own, would admit a stale ancestor. Any scheme counting or tagging self-invalidations needs an atomic native contract and exhaustive concurrency tests; no such contract was found. Revision increment occurs before `finishWrite`, so the increment alone does not prove persistence.

After `store.commit` returns, `updateTrust` marks `persisted`, permits precisely its own `revision + 1`, checks its role and view, and advances the epoch; any subsequent failure is converted by `uncertainTrustCommit` to `VAULT_COMMIT_UNCERTAIN` and locks the vault (`AppSecrets.java:2205-2229`, `:2257-2262`). The exact retained attached view is not revoked by this own epoch advance, but still contains old file bytes. `ChildTrustSnapshot` also fixes its old epoch and revision (`SshManagedKnownHostsProvider.java:200-215`, `:236-240`) and a successful provider write closes its source receipt (`:778-796`). The existing `TrustCommitState` uses distinct one-shot receipts per hop and `confirmTrust` orders acknowledgement against cancellation (`SshPasswordConnector.java:298-334`, `:483-517`; `SshSessionOwner.java:56-72`). A NEW pending protocol needs a deliberate acknowledgement of the exact signed milestone and successful CAS before cleanup, without manufacturing an ordinary credential-authorizing proof.

### Reconnect and UI publication are separate requirements

`SshPasswordConnector.create` is one-shot, fixes `connectionId`, original revision/config binding and cancellation, and calls `createJumpConnection` once (`SshPasswordConnector.java:115-119`, `:135-157`, `:622-637`). `check()` treats a changed revision while `jumpHops != null` as failure (`:1943-1953`). The old owner, children, callbacks, candidate source and shared lease must be closed in reverse order; `closeJumpConnection` deliberately retains partially closed owners for retry (`:1225-1249`). Blindly advancing a field or recycling the old source is insufficient.

An explicit new attempt is a smaller potential product increment than invisible auto-reconnect, but it requires a complete result/cleanup contract:

1. Only after the exact KEX-bound CAS and one-shot trust confirmation are known successful, retain a non-secret, non-replayable completion outcome scoped to this owner; uncertainty, lock, cancellation before confirmation, deadline and failed write must not be turned into a success message.
2. `SshSessionOwner.create` currently completes its `connected` future exceptionally before `closeUnattached` runs (`SshSessionOwner.java:186-206`); close retries on its owner executor when needed (`:335-345`). The bridge clears `active` when that future completes (`SshPasswordConnectBridge.java:473-506`), but `SshSessionService.attach` refuses while its static owner is non-null (`SshSessionService.java:68-75`). Thus immediately asking the user to retry can produce BUSY before cleanup completes. A new result protocol should either delay the retry-ready result until exact cleanup and service release, or expose an explicit cleanup-pending state and keep retry disabled until a trusted release notification.
3. Service release itself has an additional asynchronous boundary: `releaseOwner` calls `stopSelf` while the service exists, and the static owner is cleared by the matching `onDestroy` (`SshSessionService.java:275-296`). Completion of the native cleanup or `Lifecycle.released` alone is not necessarily readiness for a new attach. Do not simply clear the owner early: the old service's `onStartCommand` ignores a new START while its `attached` remains non-null (`:179-202`). A service-level completion bound to that exact owner and completed after the static owner is actually cleared is one candidate; failure, cancellation and service destruction still need explicit tests.
4. The connector's final result, owner terminal events and form events are different channels: owner failure events use `ctos/terminal`, while the form bridge publishes the actual completion code on `ctos/ssh` (`SshSessionOwner.java:186-205`, `SshPasswordConnectBridge.java:477-506`, `MainActivity.java:74-84`). Do not assume the generic terminal failure automatically overwrites the form; test both channel orderings. `VAULT_COMMIT_UNCERTAIN` remains higher priority than deferred screen lock/service start or retry-ready (`SshSessionOwner.java:186-202`; `SshPasswordConnectBridge.java:490-520`). A cleanup failure must not manufacture confirmed trust or permit an unowned retry.
5. A saved trust CAS invalidates the currently selected config binding: `configBinding` includes snapshot binding, epoch and revision (`SshConnectionMaterial.java:524-527`). Merely re-enabling Connect with the old `_configHost` will fail `VAULT_CHANGED`. Either explicitly require reopening and reselecting the config, or reload defaults/library and revalidate the alias and actual host, port, username and policies before creating a new request. Existing restore/revalidation logic compares those fields (`password_connect_page.dart:308-339`, `:407-426`, `:742-750`, `:915-935`). Never preserve a stale authorization or auto-use a prior secret.

An automatic retry within the same request additionally conflicts with current Flutter monotonic event checks: after a target review at hop 1, a new hop 0 password event has `event.hop < _lastReviewHop` and invalidates the attempt (`password_connect_page.dart:1758-1770`, `:1881-1903`). A fresh authenticated attempt-generation protocol or a new user-visible request is required. A new request resets these counters and obtains fresh request ID at `:1445-1460`; each saved password must be explicitly approved again and the original timeout must not be silently renewed by an internal retry.

### Suggested verification before enabling the path

- Barrier tests at exact native/KEX completion, final admission, `AtomicFile` guard, real store outcome, ledger notification and final confirmation. Exercise owner Stop, ancestor/child cancellation, role close, view revoke, lock/background/expiry and unrelated vault modification both before and after each boundary; verify no trust write if revocation wins admission and preserve `VAULT_COMMIT_UNCERTAIN` whenever a write may have happened but cannot be confirmed. Include same-thread invalidator/permit deadlock checks and prove no permit is held during fsync/finishWrite.
- Bind review, candidate, source identity/path, both digests, role/hop/endpoint, KEX cycle/session digest, owner and generation; reject direct calls, replay, mismatched candidate and stale or foreign owner. No credential, userauth or shell before a confirmed known-host path.
- Exercise owner cleanup fail-then-retry, service `onDestroy` delayed, Stop/screen-lock/service rejection during pending cleanup, main-thread event/RPC reordering, bridge destruction and attempted early reconnect; only the exact released owner can signal readiness. Test the fresh config binding and changed alias/host/port/user after an own trust CAS, including no automatic reuse of saved passwords.
- Separate real encrypted-vault Store behavior, production JNI/native with synthetic peers, and the local `--network none` two-sshd product fixture. Real-server NEW success and no-target-secret-on-reject are required once implemented; Android device and UI MethodChannel evidence remain separately scoped.

### Alternative investigated: seal signed trust, retire the chain, then write

**Assessment:** This can eliminate the need to continue authenticating or pumping on a jump chain after its own trust CAS changes the vault and effect generation. It is not supported by the present code and does not by itself solve authorization, cancellation, or lock ordering. It deliberately changes the authority boundary: after an authenticated one-shot handoff, the eventual writer would rely on a new detached trust capability, not on a currently active SSH role/view. That transition must be explicit in design/spec and tests.

1. While the exact child/parent/relay remain owned and valid, require user approval, the actual offered-key signature and inbound NEWKEYS, the exact KEX cycle/session digest, source receipt/digests and any required outbound drain. A distinct real-native milestone is still necessary; current child NEW and ordinary `completed`/`Proof` are not that milestone. Capture the actual generation **before** live checks, then use a short matching generation permit to atomically publish a preconstructed immutable, once-only detached receipt. No JNI reentry, blocking callback, disk I/O, role/view/session/cancellation monitor or user event may run while holding this permit. The receipt must be issuable only by the exact real callback/session owner, not by channel data or a caller-provided boolean. The permit acquisition and revocation ordering need a concrete proof; this is not implemented.
2. Transfer, rather than duplicate, authority and the exact bounded replacement candidate. `closeJumpConnection()` destroys child session, callback, handoff, provider, source, role, shared view and registry (`SshPasswordConnector.java:1225-1249`). Provider `failClosed` cancels its context/request and wipes its candidate and proposal (`SshManagedKnownHostsProvider.java:907-935`); native close can abort a handed-off candidate if the client is not ordinarily completed (`ssh_native_client.c:4493-4519`, line numbers may shift during concurrent native edits). A new one-shot handoff must consume the old owner/candidate so neither the retired provider nor a second receipt can write. Hold no secret credential in the detached object; wipe the candidate copy on consume, cancellation, failed cleanup, expiry and destruction.
3. Existing role-bound authorizations **do not survive intentional teardown**. `SnapshotReceipt.requireLive()` invokes the old role's `requireActive` (`SshManagedKnownHostsProvider.java:103-110`), `SshVaultAdapter.requireTrustBinding` requires that role and receipt (`SshVaultAdapter.java:247-263`), and role closure or view closure makes these checks fail (`SshRoleContext.java:135-146`, `:191-195`). This is correct behavior and must not be loosened. The detached receipt needs a new narrowly scoped operation/binding that records the original exact role/source facts without asking the retired role/view to remain live. Existing role-less compatibility overloads lack signed-key and real-source authorization and are not a safe substitute.
4. Planned cleanup must not use `SshPasswordConnector.close()` unchanged: it calls `cancel()` first (`:2030-2034`), which cancels the shared owner and vault-origin context (`:552-577`) and would revoke the detached operation. A dedicated planned-retirement state must distinguish owner-requested cleanup from real Stop, lock, background and deadline. It must keep the actual original cancellation authority and protected request alive until the write outcome is confirmed, retain cleanup owners across failures, and never start the write if cleanup was incomplete. An external revocation winning before sealing must prevent issuance; treatment of a role/view/ancestor revocation after sealing but before planned teardown needs an explicit policy and a mechanism to distinguish it from intended retirement rather than assuming every invalidation is self-caused. In particular, a single sampled global generation cannot distinguish two invalidators merely by their reason.
5. The detached operation must bind the authenticated original vault ID/binding, epoch, revision, validator, exact known_hosts object identity/path, base/replacement digests, endpoint, fingerprint, KEX/session evidence, owner, original deadline and exact cancellation/protection state. `beginTrustUpdate` currently captures the **current** revision at invocation (`AppSecrets.java:2027-2062`); creating a generic context only after teardown would silently accept intervening writes unless the new authority independently requires the frozen original revision and source ciphertext. The existing `trustCandidate`, encrypted readback, source CAS and `VaultStore` mechanics can be reused only behind the new exact operation contract.
6. `VaultSession` retains its `revocation` reference after the lease closes; it may be non-null but inactive (`VaultSession.java:83-95`; `SshPublicFileLease.java:151-154`). A current role-bound operation treats a non-null continuation as its own active view and then checks that it remains active (`AppSecrets.java:2063-2072`, `:2010-2024`), so it cannot simply be reused after close. A detached write must also prevent a newly attached unrelated active view from being silently revoked by the role-less `session.unlockIfEpoch` path (`AppSecrets.java:2209-2219`; `VaultSession.java:33-38`). One possible design is an exclusive, cancellable write reservation preventing new attaches; another is an exact expected-retired-view/no-active-view check under the same session lock at the final epoch transition, with an intervening conflict after a possible write treated as uncertain. Neither is implemented; both require tests for attach races.
7. When the last `JumpChildOwner` closes it disables the Java jump-effect fence (`SshNativeSession.java:1057-1060`, `:1157-1165`). Thus the detached phase must not assume `beginJumpEffectInvalidation()` is an active guard. Its final trust-write admission must instead explicitly order the original owner cancellation and vault/session lock/foreground/epoch state. A synchronized or atomic metadata-only admission is plausible after teardown, but its complete lock order with `AppSecrets`, `VaultStore`, owner cancellation, `session.lock`, callback/role cleanup and other owners must be established. The receipt needs an admitted/in-flight state visible to cancellation and owner result handling before any potentially durable effect; the actual store I/O remains outside that admission lock.
8. “Cancel before write” must name a linearization point. Cancellation that wins before final write admission can and must prevent the commit. If the write admission wins and the owner is descheduled before `AtomicFile.finishWrite`, a later cancellation can physically precede the filesystem call but cannot both guarantee zero write and avoid holding an unbounded lock across I/O. Treat an admitted operation whose outcome cannot be confirmed as `VAULT_COMMIT_UNCERTAIN`; never claim a physical rollback. Preserve `mayWriteTrust`/deferred result tracking until the transaction settles.

Tests for this alternative must distinguish intentional teardown from real cancellation and revocation at every handoff/close step; deny a stale/mismatched/double-consumed detached receipt; inject partial cleanup, owner Stop, screen lock, background, deadline and vault update before and after final admission; race a new view attachment; and verify no password or shell effect, no premature success, no false rollback and no deadlock. Successful write must refresh config binding before an explicit new request as described above. Device/service lifecycle and real-server tests remain separate from synthetic native/JNI and in-memory vault tests.

## Caveats / Not Found

- No complete provisional NEW, after-step commit admission, ancestor-wide trust-write fence, committed-receipt-to-cleanup handoff, service-release future, or automatic connection rebuild was found. The suggested admission mechanism is a design direction, not a proven patch.
- The current actual product route rejects NEW before any trust write; the existing direct NEW and CHANGED implementations do not establish child-chain safety. Tests quoted above use different mixtures of fake native bindings, in-memory Store and host fixtures; no new test was run by this research.
- Process-wide generation can conservatively affect another owner; the current UI enforces one SSH service owner, but the scope needs review before allowing concurrent owners.
