2026-11-18：用户确认指定开发板上当前服务器驱动连接流程通过逻辑验收，并要求继续。沿 R10 推进自动提示内可选的密码与私钥口令保存及复用。完整父任务验收范围沿用下文。[用户反馈](../../../design/verification.md#20261118-ssh-server-driven-acceptance)。

## 2026-11-16 用户修正：按服务器要求完成整个 SSH 连接

用户要求沿主机 OpenSSH 的心智模型调整现有模式：加载／输入用户、主机、端口，私钥
可选；连接和指纹核验后按实际服务器要求询问密码或展示真实问题；只允许公钥而没有
可用私钥或凭据错误时明确拒绝。无需用户预先选择“密码／服务器交互式认证”作为连接
模式。服务器可能逐步返回后续因素，不能声称提前知道完整认证结构。

这是新连接流程目标，不是单独开放一个首方法探测入口。[设计及待实现验收](../../../design/ssh-server-driven-authentication.md)。
保留旧 KBI 首方法入口，直到新路径完整实现并验证；当前未提交的 SSH 与其他任务改动保留。
自动模式本次输入与兼容模式中原有的保存／复用入口分别保留；自动提示本身暂不提供
保存或复用。真实 Android JNI、指定板和真实服务器不能由本地分层验证推定。

## 2026-11-16 接续：KEX 主机证明失败诊断

沿父任务 R4／AC4 修正已知诊断缺口：仅将同一次 KEX 回调中的固定主机证明绑定
失败，在原连接、原秘密库上下文及实际传输期限仍有效，且本次尚无受跟踪的凭据／

用户在指定板体验当前 `b3db3b40…` 后指出，连接页排版不协调；选择配置主机时又

从用户视角，config 首先提供目标、用户名、端口及未来可能支持的跳板；选择配置时
不应突然要求决定认证方式或私钥，应该回到连接页再统一处理认证。

用户还指出指纹变化弹窗排版不好，以及首次连接时普通用户无法理解为何要预先勾选
“按服务器要求继续交互式认证”；未勾选导致服务器要求后续认证时失败，即使错误提示
说明了要重试也不符合预期。截图仅证明弹窗显示了新旧指纹与实际信任来源，及某次私钥
尝试显示续接提示；不能据此推断本轮完成了换键信任写入、后续认证或进入终端。

本轮已明确的体验目标：

1. 配置主机入口只负责选择目标；返回同一个连接页后再选择密码、私钥或独立服务器
   问题认证，仅在需要私钥时选择实际密钥。切换、取消、返回后保留明确的选择与
   来源绑定；配置／密钥改变、失效或用户取消不得静默退回手动目标或其他认证。
2. 重新整理连接页的目标、认证、凭据和主要操作层次，避免过多重复字段与突兀的
   全宽操作；兼顾现有深色主题、手机／横屏／大字号和键盘操作。
3. 指纹变化弹窗重新设计信息层级与间距，但仍展示实际目标、完整新旧指纹和实际
   信任来源；保留明确选择、取消、受保护记录限制、同连接签名与精确来源 CAS。
4. 避免普通用户必须提前理解服务器后续认证：用户已选择服务器确实要求追加认证时，
   在同一次连接中直接显示真实服务器问题，由用户输入或取消。不得自动填写、保存或
   推断验证码，不把首方法 PARTIAL 当作最终登录成功。

技术边界：现有 `continueKeyboardInteractive` 一旦开启，会在连接准备阶段检查 config
链式顺序；仅将其默认改为 true，会让只需首方法即可成功的合法配置提前失败。本轮须
在真实 PARTIAL、服务器方法列表和实际配置政策均允许时才考虑后续阶段，不将普通
拒绝变成对已提交凭据的误判。当前没有首方法前 `none` 探测；本轮优先基于真实
PARTIAL 和允许方法自动续接，独立服务器问题首方法继续可用，不宣称已自动发现
KBI-only 首方法，也不在错误密码后盲目重试。更广的发现机制另列后续能力。

本轮目标验收：

- 手动和 config 入口均在连接页选择认证；从任一入口选择 config 后不插入认证弹窗，
  配置目标、用户名与端口真实可见。只有选择私钥后才要求选择实际私钥；取消或对象
  变化时保留经精确重验的原选择或要求重选，不静默降级为手动密码。
- 密码／私钥首方法成功即可进入终端；实际部分成功、服务器列出支持的后续方法且
  配置允许时，直接在同一连接显示问题，无须预先勾选或重连。服务器普通拒绝、后续
  方法不支持或配置不允许时清楚失败，不能自动尝试其他凭据；独立服务器问题可用。
- 换键弹窗可完整核对目标、新旧指纹及实际来源，明确确认后继续同一连接，取消不写；
  签名校验、精确来源替换、受限记录和原有保护不因重排而放宽。
- 连接页与弹窗覆盖宽屏、窄屏、横屏、键盘和大字号；覆盖配置／密钥漂移、取消、锁库、
  后台及迟到结果。分列本地 Flutter、实际协议、秘密库、JNI/Android 和人工体验证据。

本次不增加跳板、真实账号操作或任意重复凭据尝试；新候选的设备安装和人工验收单独
处理。上述历史 1008 主任务与已授权增量保留；尚不表示产品修改、测试、安装或人工验收已完成。

## 2026-11-13 用户反馈：简化指纹变化后的连接

用户在配置主机私钥续接测试后反馈“功能通过”；该反馈按本次配置主机／私钥／续接
范围记录，不推断其逐项执行全部异常流程或完整父任务验收。用户指出截图中的旧指纹
对话框繁琐，从进入 SSH 到处理旧指纹、确认新指纹和连接要点近 10 次，心智模型不清楚。

用户选择的目标：常见指纹变化场景中，在同一个界面核对新旧指纹，明确选择“信任新
指纹并继续”后，应用完成必要的旧记录处理并继续连接；保留取消。目标是减少重复的
用户决策，而不是把两组相同文字的记录擅自当成同一个存储对象。受保护／共享记录、
实际信任来源、并发改变和真正成功前的凭据门禁仍须根据实际实现研究并纳入方案。

拟议范围与验收：

1. 常规可安全替换的变更只需一次明确决定：展示实际目标、旧指纹、本次收到的新指纹；
   用户确认后继续当前连接，不再经过忘记、成功回执、手动重连和重复确认新指纹。
   连接结果直接显示为认证、终端或明确错误；服务器额外问题仍由用户回答。
2. 根据本次连接实际求值得到的信任来源操作；只修改审阅范围内的普通单目标记录，
   其余来源／主机／记录保持。共享、通配、吊销、CA、不支持等原受保护情形不绕过。
3. 明确同意只授权本次收到且展示的 key。握手签名和原来源绑定的安全提交成功前，不
   向远端认证流程交付所选凭据；拒绝／取消／锁库／超时、签名失败和来源变化不继续
   认证。持久写入不确定时按现有保护锁定并明确告知，不把结果假定为回滚或成功。
   本地密钥检视及用户明确选择的保存动作仍按既有合同处理。
4. 在连接目标区域提供配置主机快捷入口，避免先展开资料管理并浏览完整资料页；仍需
   显式选择认证方式及实际私钥。取消选择时不将临时秘密带入新请求，并保证公开选择
   重新验证后可恢复；配置失效时明确提示而不静默改用其他身份。
5. 覆盖手动与配置入口、密码／私钥及续接能力，窄屏／大字、返回／后台和失败场景；
   分列真实合成协议、native/JNI、宿主、Flutter、构建及后续设备／人工体验证据。
   首次连接、普通可信主机、手动独立管理入口及锁屏后的手动重连保留原有语义。

该方向对下方历史“忘记后必须手动重新连接”的交互约束提出明确变更；其他历史认证、
信任和生命周期约束不因此取消。用户在审阅完整范围、单次确认、安全边界、快捷入口和
验证计划后选择“按方案实施”；本轮进入实现，尚未完成或安装。

## Background

已核实的当前行为：

- 终端只有“应用 Shell”和“Root PTY”，共用 xterm、底部输入、五个快捷键及输出选择页。入口在 `lib/main.dart:1671`，输入组件在 `lib/terminal_interaction.dart:9`。
- JNI 的启动参数固定为 `/system/bin/sh -i` 或 `su -p`，不能直接启动任意客户端：`android/app/src/main/cpp/pty.c:18`。
- APK 内置 Python 3.13、cryptography 等依赖，当前 Dart/Gradle 依赖没有 SSH 客户端：`pubspec.yaml:8`、`android/app/build.gradle:35`。
- Portable 工具从 APK 原生库目录执行，配置/资源放 App 私有目录，禁止包覆盖 HOME：`android/app/src/main/java/im/majo/ctos/PortablePackages.java:61`、`:205`。
- 生命周期文档与当前源码存在差异：`MainActivity.java:320` 的 onStop 仅取消工作台 Python，`:330` 的 onDestroy 才调用 stopTerminal。SSH 服务需独立持有会话，不能照搬“已自动回收”的假设或顺带修改旧 PTY 的生存期。

## Requirements

R1–R11 汇总用户已确认的需求与达到这些目标所需的具体交付契约；原生构建、格式支持及平台行为的未实测项单列在 Technical Notes，不以规划替代验证。

- R1 / APK 能力：客户端及必要运行依赖随 APK 提供；无 Root 设备可使用 SSH，不要求 Termux、设备已有 ssh 或运行时下载。
- R2 / 终端体验：在“终端”增加 SSH 入口，参考两个已有终端，支持远端交互 Shell、UTF-8 输出、尺寸调整、Ctrl-C / Tab / Esc / ↑ / ↓、输出搜索和复制。SSH 连接后用户输入及控制键交给远端处理，↑/↓ 不由 ctOS 本地历史截获；远端程序自身定义操作，ctOS 不追加程序专属逻辑或用户切换模式，不设特定远端程序的兼容验收。本机 App/Root 终端不回退。
- R3 / config 与一键连接：config 是连接配置的权威来源；从明确的 Host 别名生成主机列表，显示别名和解析后的目标，点选后发起连接。通配规则参与匹配，不伪造为具体设备。一键连接允许首次主机确认及必要认证交互，不承诺无密码操作。
- R4 / 状态与恢复：区分连接中、待确认、认证中、已连接、失败、主动断开、远端退出；可取消连接或重试，禁止重复连接、跨会话输入和远端输出冒充本机状态事件。
- R5 / 已确认认证与信任：未知主机展示实际地址、端口、算法与 SHA256 指纹；用户接受后保存信任记录，指纹变化阻止正常连接并提供核验恢复。config 不能跳过核验，no/off、自动接受未知指纹等违反该规则的有效选项报错并阻止受影响连接，不静默替换；根文件、Include 及每一跳一致执行。认证秘密不得进入命令历史、输出快照、日志或普通配置文件。

- R11 / 已确认 App 统一秘密库与公共认证：用户最新明确把 Authenticator 主口令/便携加密库/可选生物快捷解锁/覆盖迁移模型应用到 SSH。公共 AppSecrets 统一 KDF、持久化、设备包装、库会话/代次与迁移；AppAuthentication 统一系统可用性、UI、用途/目标绑定、并发、生命周期、错误及受保护操作。SSH/TOTP 使用同一底座和解锁入口，各自只拥有受限业务 adapter，不返回通用密钥或全局已认证布尔值。主机信任/远端登录/Root/SAF 仍独立，不自动改造无关功能或导出跨 App 接口。此决定替代原设备绑定秘密库和 SSH-only 每次系统验证方案，公共会话/设置/备份/管理口令与隐私配套范围已确定，当前待共同最终审阅。
