# Research: explicit private/public/certificate pair verification

- Query: Find the smallest reusable synchronous verifier of actual private bytes, an exact optional passphrase, and actual PUBLIC_KEY/CERTIFICATE bytes, including a real signing-capability proof.
- Scope: internal; pinned upstream primary sources inspected locally. No builds, target execution, network, device, environment inspection, or git operations.
- Date: 2026-10-23
- Active task: `.trellis/tasks/10-08-ssh-terminal-client`; research-only role. Task PRD/design top, project design landing/plan/constraints and relevant backend spec were consulted; role-isolated `implement.jsonl`/`check.jsonl` were not loaded.

### What can and cannot be reused

1. `ssh_material_inspect.c:98` enforces one exact private armor envelope and only CR/LF after its end; `:133` only reads the OpenSSH encryption header. `:162` checks that an unencrypted PEM's decoded top-level ASN.1 SEQUENCE occupies the decoded bytes. Existing PRIVATE parsing at `:192` combines those checks with shared encrypted policy, missing/bad passphrase results, pinned private parser and software policy. Refactor its internal parsing into a shared owned-key result rather than copying this grammar into another module. The new verifier can live in this same C file and reuse its static helpers; preserve existing CSMIv1 semantics exactly.
2. Public parsing at `ssh_material_inspect.c:233` permits blank/comment lines and exactly one physical key record, with standard trailing comment text. Pinned `sshkey.c:1299` decodes its base64 token with `sshkey_fromb`; `:2063` rejects leftover decoded public/certificate blob bytes. Keep the same grammar and declared PUBLIC versus CERT type check. A second physical record is malformed; trailing comment text is allowed by this grammar and is not another association input.
3. `ssh_key_policy.c:55` rejects certificate types, SK keys, external-provider flags, non-Ed25519/EC/RSA keys and RSA below the pinned floor. Therefore apply this shared policy to the PRIVATE key and a *plain public subject* copied from the peer, not directly to a certificate object. `sshkey_from_private` at pinned `sshkey.c:1598` copies public fields and certificate data even when its argument is already public; `sshkey_drop_cert` at `:2288` frees the certificate and changes its type to plain. Copy then demote preserves the original parsed certificate and avoids broadening shared policy.
4. Pinned `sshkey_equal_public` at `sshkey.c:817` explicitly permits plain-versus-cert comparison but only compares public fields. Ed25519 private deserialize at `ssh-ed25519.c:120` reads public bytes and a length-checked 64-byte secret without deriving/checking their relationship. Its signer at `:146` uses the secret. OpenSSH private parsing at `sshkey.c:3239` checks envelope/public equality, which still does not prove the secret can sign for those public bytes. A challenge signature verified by the peer subject is essential.
5. Existing `ssh_native_client.c:1151` checks software policy and public equality, then `:1173` signs actual SSH USERAUTH data, checks signature type/length and `:1180` locally verifies against the expected key. Reuse those pinned primitives and policy, not the entire live authentication function: that function consumes proof-bound credentials, username/session context and sends an authentication packet. An offline pair verifier must create none of these capabilities or effects.
6. Pinned `sshkey_sign` at `sshkey.c:2212` can dispatch to SK/PKCS11 for corresponding keys. Enforce software policy first, pass no provider/PIN, use an explicit plain algorithm, and retain no caller-selected signing payload. For RSA choose a frozen SHA-2 algorithm such as `rsa-sha2-512`; do not pass NULL and permit a legacy SHA-1 default.

### Proposed minimum native operation

`ctos_ssh_material_verify_pair(peerType, privateBody, privateLength, passphrase, passphraseLength, peerBody, peerLength, originalDeadline, output)` can be synchronous and borrow bounded slices. The only supported peer types are actual PUBLIC_KEY and CERTIFICATE. No file/path lookup, registry/view, role/session, environment, provider, command, DNS or network input is needed.

Process: validate API bounds and original deadline; perform bounded text/envelope/header checks; apply strict pair policy before any private parser/KDF; parse the actual private bytes and exact supplied phrase; parse the actual peer bytes and type; clone/demote peer subject; apply shared software policy to both; compare public fields; then sign and verify an internal domain-separated challenge using that subject. Only final successful verification produces MATCH.

Use a fixed versioned internal challenge, e.g. a framed `ctos/ssh/offline-pair/v1` domain plus the canonical plain-subject blob/digest. Never accept arbitrary caller message data, reuse SSH USERAUTH framing or return the signature/challenge/private-derived bytes. A fresh nonce is optional for this private, non-exporting proof, not needed to turn equality into a real signing check; adding randomness would introduce another behavior to freeze. Bound and wipe signature/challenge buffers on every exit. `sshkey_check_sigtype` plus `sshkey_verify(subject, ..., explicitAlgorithm, 0, NULL)` follows the existing native authentication pattern. A signature failure cannot fall back to public equality.

Pinned certificate parsing already verifies the certificate's embedded signature using its embedded signing key (`sshkey.c:1976`); a structurally signed certificate is still not trusted. Pair MATCH only proves that this private key signs for this parsed certificate's subject. Do not call certificate-authority/time/principal/trust checks, create a trusted CA conclusion or imply remote acceptance. Original full certificate blob SHA-256 from `ssh_material_inspect.c:62` differs from a plain subject digest; use the canonical demoted subject blob for any new association digest.

### Exact passphrase selection and strict completeness

`VaultManifest.java:175` gives IDs global uniqueness; `:209` forbids non-CONFIG references. Its `:212` passphrase check establishes only that some PRIVATE_KEY has a matching `key:` identity. Neither file identity nor a `.pub`/certificate filename establishes a pair. Introduce caller input `Pair(privateFileId, peerFileId, passphraseEntryId?)`, resolving exact IDs in the actual supplied manifest loan. Require the private/peer types, exact passphrase entry type, nonempty no-NUL phrase within 8192 bytes, and the selected phrase's existing `key:` metadata compatibility with the selected private. The metadata check is a selection policy, not mathematical evidence.

An explicit phrase ID resolves selection even if other entries share its identity; do not copy/use those other secrets, retry candidates or pick the first. An omitted ID remains omitted even if matching-identity entries exist; encrypted input returns NEEDS_PASSPHRASE. Existing material-inspector AMBIGUOUS_PASSPHRASE behavior at `SshManifestInspector.java:167` remains unchanged because its API uses implicit identity selection. Exact IDs select caller intent; successful decryption/signing tests the selected bytes.

Current manifest secrets are nonempty (`VaultManifest.java:179`), so a native zero-length phrase can unambiguously mean omitted. For an unencrypted private key, reject an explicitly supplied nonempty phrase as UNSUPPORTED at PRIVATE_POLICY (or reject that Java selection explicitly); never silently ignore it and return a result that appears to validate the phrase. BAD_PASSPHRASE remains the upstream decryption error category, which may also mean damaged ciphertext, not a claim about user error (`sshkey.c:3560`).

The smallest strict pair policy should reject all recognized traditional encrypted RSA/EC PEM **before** private parser/KDF, even with no phrase, as UNSUPPORTED/PRIVATE_POLICY. Existing `ssh_material_inspect.c:200` explicitly bypasses decoded-DER completeness for encrypted PEM. Pinned `sshkey.c:3560` uses `PEM_read_bio_PrivateKey`, which does not return the consumed decrypted-DER cursor here; no existing shared helper proves complete consumption. Reusing it cannot establish that encrypted suffix bytes were consumed. Do not add another PEM decryptor in this increment or change existing inspector/auth accepted formats.

For accepted encrypted OpenSSH, reuse `ssh_key_policy.c:163` framing and its exact one-key/aes256-ctr/bcrypt/salt 1..64/rounds 1..64 policy at `:171`. Pinned `private2_decrypt` rejects trailing decoded envelope data at `sshkey.c:3164`; `sshkey_parse_private2` consumes the private object/comment and checks deterministic remaining padding at `:3230`. Unencrypted PEM retains the existing complete top-level DER SEQUENCE guard; this is not a new general DER canonicality proof. Unsupported PKCS8/KDF and CRLF limitations must remain explicit rather than normalizing supplied private bytes.

### Status, wire and lifetime recommendations

A separate fixed 60-byte `CSKA` v1 avoids reinterpreting old CSMI. A possible exact layout is seven big-endian u32 fields (magic/version/status/stage/peerType/kind/flags) then 32-byte plainSubjectDigest. Freeze constants and all valid combinations before implementation. Proposed statuses: MATCH, MISMATCH, MALFORMED, UNSUPPORTED, NEEDS_PASSPHRASE, BAD_PASSPHRASE. Stage distinguishes PRIVATE_POLICY/PRIVATE_PARSE/PEER_PARSE/PUBLIC_COMPARE/SIGN_PROOF/DONE so a public-field mismatch differs from a failed private signing proof without exposing secrets. Non-resource signing/verification failures must remain material failures (MALFORMED or MISMATCH as explicitly frozen); they never become MATCH.

Only MATCH should carry kind and a nonzero subject digest. Keep all non-MATCH digest/kind zero; peerType is the validated requested PUBLIC/CERT type. Freeze encrypted/certificate/pairs-only flag combinations rather than copying permissive CSMI rules. The wire contains no phrase/private digest, signature, full key blob, pointer, descriptor or authority. Invalid arguments, memory/libcrypto/system errors, cancellation or deadline expiry return failure, clear output, and publish no partial successful report. Java must independently reject unknown values, bad lengths, forbidden flag/status combinations, trailing bytes and success fields on failure.

Reuse the original absolute CLOCK_BOOTTIME deadline (at most 60 seconds); never mint a new deadline per pair, parse, KDF or JNI call. Keep one aggregate work budget/count bound so repeated explicit pairs cannot reset work limits. Cancellation must be checked around copying, each native call, cleanup and final publication. One bcrypt/sign/verify call remains synchronous and cannot be interrupted; 64 rounds is a cap, not a guaranteed wall-clock completion time. Expiry/cancel during that operation blocks subsequent work and publication. Existing C material API checks deadline before/after (`ssh_material_inspect.c:39`, `:324`); Java checks after loan cleanup at `SshManifestInspector.java:185`.

Java should snapshot the Pair list and selected metadata/bodies/phrase into exclusively owned cleanup slots before use, read actual source/target/candidate bytes rather than current store, avoid unrelated password/TOTP copies, reject duplicate/conflicting exact selections under a frozen policy, and return immutable `pairsOnly=true, admissionComplete=false` metadata. An empty explicit pair list proves zero pairs. Do not imply all private/public/certificate files are associated, add a persisted association format, register a production validator or open recovery/provider admission.

Existing `ssh_material_jni.c` copies into bounded calloc scratch and wipes/frees it; this is not locked-memory ownership. Mirror its preallocated output array, independent input checks, pending-exception preservation and post-write deadline check if reusing that JNI pattern. Any stronger mlock/retry-close ownership claim would require a separate contract and evidence; synchronous local scratch currently has no persistent handle.

### Verification obligations for implementation, not performed here

- Actual positive/negative software algorithms, RSA floor/SHA-2 and equal-algorithm different keys; PUBLIC/CERT type errors; same/different certificate subjects; expired/untrusted but parsable certificates demonstrating no trust claim.
- A syntactically accepted Ed25519 private container whose serialized public bytes match the peer but whose secret does not; it must fail the actual challenge proof. Include parser-accepted corrupted secret cases without assuming every algorithm permits their construction.
- Exact selected phrase succeeds; omitted ID never auto-selects; wrong phrase/corrupted ciphertext classification; multiple same-identity entries with explicit ID; clear key plus supplied phrase; legacy encrypted PEM rejected before KDF; bounded encrypted OpenSSH and over-limit rounds.
- Single-envelope/decoded trailing data, extra public record/comment rules, NUL/size/line limits, invalid wire combinations, aggregate pair budgets, original deadlines/cancellation after crypto/cleanup, injected allocation/publication failures and complete wipes.
- Existing full native authentication/PTY regressions after any shared parsing/policy refactor, material inspector compatibility, effects/capabilities observers, JVM actual-candidate ownership/codec tests and required native/JNI/build/APK gates. This research ran none.

## Caveats / Not Found

- There is no current authoritative persisted non-CONFIG private/public/certificate pairing field. Explicit Pair IDs provide a useful checked subset, not full graph association coverage. Future full semantic validation still needs association authority/coverage, config-selected effective identity/certificate relationships and complete private material policy.
- The current non-TOTP `identity` regex permits `target:` or `key:` strings (`VaultManifest.java:186`); SSH_PASSWORD has no dedicated normalized target/account/username fields. Live `SshAuthenticationSelection.java:37` separately supplies username and exact password entry, and `SshCredentialBridge.java:102` uses a live role target. These live constraints do not prove a stored password belongs to that target/account or that it is correct. Keep password target/account validation, canonical model/migration, per-hop selection and remote authentication as explicit future obligations; do not parse invented username semantics from an identity string.
- Certificate CA trust, current validity, authorized principals, critical-option applicability, revocation and remote acceptance remain outside pair proof. No trust/recovery/provider or complete-client acceptance conclusion follows.
- External reference/version: only locally pinned OpenSSH 10.6p1 sources above were used as primary evidence. No external docs were fetched, no toolchain/runtime version was revalidated, and no new execution evidence is asserted. Main should capture its fresh baseline and freeze the final public contract before implementation.
