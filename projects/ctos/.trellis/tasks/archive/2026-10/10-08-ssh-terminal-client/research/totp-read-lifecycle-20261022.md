# Research: TOTP typed-read lifecycle and final publication

- Query: Map the next outside-core typed read migration: TOTP list/code admission, operation effect, Bridge result/clipboard publication, original request cancellation/deadline, ownership and locks. Identify a minimal coherent contract; main session freezes the final API and claim semantics.
- Scope: internal; read-only source/design/spec research. Only this research artifact was written; no agents, builds, tests, network or devices.
- Date: 2026-10-22

Source line references and current-behavior findings below describe the pre-implementation
research snapshot. The frozen implementation contract is design/totp-read-lifecycle.md;
subsequent actual results are recorded in design/verification.md.

### Actual original Request and operation flow

1. Main admits the request ID (read iff `secrets.totpList`), constructs Request with current session epoch, sets `active`, starts 120-second timeout, and queues worker (`AppSecretsBridge.java:242-260`). `Request.deadline` is created once at field initialization with elapsed realtime (`:83`); it already includes worker queue delay.
2. `Request.phase` is created once (`:67`); `Request.cancel()` only cancels that phase (`:118`). Timeout and explicit/lifecycle cancellation call it immediately before queued preview cleanup (`:248-256`, `:917-925`). There is currently no private TOTP context to cancel before an operation exists.
3. Worker `guard(request)` checks closed/phase/active, deadline, then `session.assertEpoch`, then resumed/foreground (`:435-440`). Outside a phase fence this lazy-epoch call can revoke on an expired background session; inside a phase fence foreground must precede it.
4. `requestGuard(request)` retains the original Request. `check` calls guard; `beforeCommit` claims its existing phase; `publish` orders phase -> session, checks resumed/foreground **before** guard and invokes only the supplied publication (`:524-540`). Its lock topology must be respected, not reused for a read callback that then takes publicationLock. Add a read-specific origin guard whose `publish` takes the original phase only; retain the existing hook for bundle/preview/mutations.
5. List currently calls `beginTotpList()`, `totpList(op, wallSeconds)`, `totpPublication(op)`, queues main result, and stores `wallSeconds/30` (`:280-285`). Copy calls adapter `request(id)`, code generation, `totpPublication`, then main clipboard/result (`:312-328`). Neither admission receives the original epoch/deadline/guard.
6. `beginTotp`/`beginTotpList` use `sessionManifest` and eventually `operation`, which mints a **new** epoch and `clock.now()+120000` only after validation (`AppSecrets.java:591-599`, `:696-700`, `:1221-1227`). Queue/validation time is lost from the operation authority even though Bridge's final main guard still has its earlier deadline.
7. `verifyOperation` rejects cancelled/mismatch first, checks epoch/foreground/deadline and actual vault UUID/generation/binding, then consumes/removes (`:1231-1245`). Wrong consumer/resource does **not** consume. In list/code, verification occurs before effect's `sessionManifest`; failures during effect validation therefore already consume. `totpCode` also consumes before rejecting negative time (`:1034-1037`). Preserve accepted-attempt consumption, not successful-only consumption.
8. `protectedEffect` rereads storage, then checks epoch/foreground/deadline/cancel (`:1247-1255`). List/code run it after generation; `totpPublication` does it again and returns revision (`:636-638`). A consumed operation is deliberately still usable for the final snapshot check; that helper is not a replayable secret-release capability.

### Concrete unsafe or incomplete boundaries

- Core monitor covers `beginTotp`, `beginTotpList`, `totpList`, `totpCode`, and legacy `validateBusiness` (`AppSecrets.java:591`, `:598`, `:601`, `:1034`, `:231`). `sessionManifest` calls the provider on the actual `Verified.manifest` (`:1264-1274`). Thus mixed-vault TOTP validation blocks core lock/registration changes, and provider mutation can alter the source that generates codes. Removing `synchronized` only from `validateBusiness` does not release the caller's lock.
- Legacy `sessionManifest` only cleans up on `VaultException`, and its inner manifest cleanup also only catches that type (`:1271-1274`). A provider RuntimeException/Error can retain key/plain/manifest bytes. New read owner must use try-with-resources/Throwable-safe failure cleanup; do not broadly rewrite this helper for all consumers in this increment.
- Final `publishTotp` locks publicationLock -> session, calls `owner.check`, runs `assertEpoch` **before** foreground rejection, then calls external publication while both locks remain held (`:639-645`). Bridge passes a simple `publicationGuard` lambda, not `requestGuard.publish`, so phase cancellation is not ordered atomically against final delivery (`Bridge:321`, `:796`). A worker-thread `phase.cancel()` can race after guard's volatile read. Reusing the existing requestGuard.publish then taking publicationLock in its callback introduces session -> publicationLock against legacy publicationLock -> session; this can deadlock.
- The current final callbacks include `clipboard.copyCode`, `request.result.success`, and completion bookkeeping (`Bridge:321-325`, `:796-798`). Clipboard invokes Android Binder (`SensitiveClipboard:21`); Flutter Result is external callback work. Main's final scope refinement preserves actual **code disclosure** inside the existing publication/session fence, outside core/phase: list Result.success contains codes, and clipboard writes codes. Copy's code-free copied:true Result and all cleanup move outside every lock. This does not establish session-lock responsiveness during actual Binder/list-disclosure callbacks.
- Foreground must be checked before `session.assertEpoch`, `session.unlocked`, or `session.epoch` inside a metadata fence. These call `VaultSession.check`, whose lazy expiry invokes `lock` and owned `revoke` (`VaultSession:20-22`, `:48-50`, `:68-75`, `:101-104`). The existing preview/bundle patterns already encode this (`AppSecrets:426-431`, `:791-801`; Bridge:531-537).
- No `store.read/current/unchanged/protectedEffect/sessionManifest` inside a phase/publication claim. `current` is synchronized and reads disk (`AppSecrets:239-243`); `unchanged` uses it (`:1336-1340`). Main publication is intentionally metadata-only. Last storage read belongs to worker before a short fence and must be followed by all metadata rechecks.
- Registration is currently reread for each legacy validation, and TOTP's scalar publication carries no registration (`:231-236`, `:636-645`). Mixed read can cross same-instance re-registration unless its immutable registration identity is carried through admission/effect/final claim. Pure-TOTP read must ignore provider availability/registration churn entirely.
- `contentRevision` increments at commit admission before durable storage mutation (`:1347-1353`), making prior reads invalid even if storage is about to change. Preserve that intentional early invalidation. Snapshot binding also matters: epoch/generation alone do not identify an in-generation content rewrite.
- `Request.clear` does not cancel `totpRead` (`Bridge:109-118`); cleanup only cancels `totpCapture` (`:835`). Late admission can create an orphan operation after Request has already timed out. A private directly cancellable context plus failed/provisional-issuance cleanup closes this gap without waiting for the worker.

### Smallest coherent proposed migration (recommendation, not frozen API)

Migrate only `beginTotp`, `beginTotpList`, `totpList`, `totpCode`, `TotpVaultAdapter` read methods and Bridge list/copy delivery. Keep management preview/mutation and SSH trust/secret-release entrypoints on their explicit legacy path; do not make `BundleContext` carry this work and do not globally unsynchronize `sessionManifest`.

**Context creation.** Add a host-only TOTP read context, with owning core, original epoch/deadline/guard, captured immutable registration identity, direct cancel flag and once-admission state. Capture the existing Request epoch/deadline at main admission before `worker.execute`; context creation should be short metadata-only work and must not wait for core/file/crypto work. An overload accepting the original expected epoch avoids silently sampling a newer epoch after a queue delay. Never create another `VaultRequestPhase`. Legacy no-context overloads may create exactly one local context at public entry, to preserve existing internal/fixture callers; Bridge must use explicit context overloads. Explicit deadline cannot exceed now+120000, and expired context fails rather than renewing.

Capture registration identity up front, but **only require and compare it for a decoded manifest containing SSH** (`hasSsh`: any non-TOTP entry or any file). A pure manifest can complete without provider and despite provider churn. Once actual mixed source is discovered, the old registration must be compared immediately before invoking it and at all later release/issuance fences; never silently adopt current provider after decode. Because operation snapshot binds the whole exact vault, its mixed/pure fact cannot change across a successful effect without binding failure.

**Capture/work/fence.** Short core capture reserves one bounded read-work slot before store/caller seams (reject recursive/concurrent TOTP read work with BUSY), checks shape and original context, and copies key + actual ciphertext + revision. Effect validates exact operation/resource/context and snapshot before consuming/removing once; accepted detached work never restores it. Release core before parse/decrypt/decode/provider/TOTP generation. Independent `Verified` source owner retains authenticated source. Mixed validator gets `VaultManifest.decode(canonicalPlaintext)` in its own try-with-resources, never the source manifest; compare loan re-encoding with authenticated bytes, reject mutation, and wipe loan on every Throwable. Source key/plain/manifest and captured ciphertext/key wipe independently. Keep slot reserved until cleanup is complete so reentrant cleanup cannot overlap a new read.

Recheck original cancel/epoch/foreground/deadline, exact work identity, and mixed registration before and after every external or costly stage. Final worker snapshot comparison runs under existing core serialization, before publication fence; then recheck after the store seam. Use same owned snapshot for generation and revision receipt; avoid a second main-thread store read. All returned code maps must contain only original metadata/code Strings, never source entries or arrays.

Admission issues an operation with original context/epoch/deadline, exact purpose/resource/snapshot and mixed-registration fact through the read-specific original `guard.publish` (phase only), then publicationLock -> session metadata; direct context cancel orders with issuance under session metadata. If the publication hook changes state or throws after provisional insertion, remove/cancel **that exact provisional operation**, preserving unrelated operations. Recheck original state outside the short fence before returning, following bundle precedent. Consumed replay should remain `VAULT_OPERATION`, rather than being hidden by an unrelated old context failure.

**Result receipt.** Prefer an opaque host-only read-result/publication receipt containing original context, source revision/epoch/snapshot provenance, mixed registration fact, code window and one-shot delivery-claimed flag. Worker list/code release and final UI/clipboard delivery both check the original context; neither is a renewed authority. Do not use free scalar epoch/revision/deadline as a new typed-read capability, and do not let `totpPublication(op)` remint unlimited read delivery authority.

The legacy `totpPublication` is also used by `TotpPreviews.publication` for management preview (`TotpPreviews:45-46`). Two minimal API options:

1. Recommended: introduce typed read-specific result/receipt and final delivery API; retain explicitly legacy management-preview scalar publication until its later migration. Bridge branches on `totpRead` vs `totpPreview`. This keeps preview candidate capabilities and its independent lifetime unchanged.
2. Smaller signature surface: keep old list/code return types and add a single receipt accessor bound to that consumed read operation, with exactly one receipt creation/claim. Still split management-preview handling; otherwise its unconsumed TOTP_SAVE operation becomes confused with a completed read. Merely adding optional guard/deadline parameters to the existing scalar final method cannot establish one-shot provenance.

### Lock/order and final-delivery decisions main must freeze

**Main-session direction after initial research:** create a read-specific origin guard with publication taking **phase only**. Final issuance/list delivery order is `original read guard.publish (phase only) -> publicationLock -> session -> internal metadata/once claim`. The core helper always owns publicationLock/session even for legacy no-op guards. Context construction takes no core lock and merely records original metadata plus volatile registration snapshot. The existing requestGuard.publish remains phase -> session for its existing consumers, and must never wrap a callback that acquires publicationLock. No session -> publicationLock or session -> phase edges are introduced.

Current `commitEncoded.beforeCommit` calls original beforeCommit first and **after it returns** acquires publicationLock (`AppSecrets:1350-1353`). This is compatible with phase -> publicationLock -> session because commit does not retain phase/session while waiting for publicationLock. Preserve this separation. Unmigrated code still holds core during store commits; new final publication must never acquire core under publicationLock. Worker issuance can start under core (core -> phase -> publicationLock -> session), with storage read strictly before phase. Main receipt publication cannot acquire core.

Foreground-first matters in core metadata before any lazy session getter. Read guard's phase publication can check only Request fields (closed/active/phase/resumed/deadline), without session methods; core checks session. Do not call arbitrary original owner guards under session. Invoke the original read publication hook outside publicationLock/session, and use only bounded internal metadata inside. Copy's copied:true Result and cleanup assert absence of core/publicationLock/phase/session. Deliberate list-code-disclosure/clipboard exceptions assert absence of core/phase, with publicationLock/session held only for actual guarded effect.

**Code-window semantics:** native copies code generated from native wall time, not a Flutter code argument. Bridge stores generation `seconds/30` and both copy and list currently reject `System.currentTimeMillis()/30000 != codeWindow` immediately before final publication (`Bridge:284`, `:315-318`, `:807-810`). The pure core `totpCode(op,id,unixSeconds)` intentionally supports supplied timestamps for RFC fixtures; do not force current wall time there and break deterministic vectors. Monotonic authority deadline and wall-clock 30s window are independent.

**Main's final refinement:** a TOTP list includes secret codes, so once metadata reservation alone must not permit later disclosure after completed cancellation/lock/registration/revision/window invalidation. Reserve once under original read phase -> publicationLock -> session. Release phase. Actual list Result.success runs only after another final metadata/window check under existing publicationLock -> session, with no core/phase held. An invalidation between reservation and actual effect rejects; it does not restore the reservation. Cleanup runs outside every fence. Unlike preview summary delivery, there is no general after-claim-invalidation permission for TOTP codes.

For copy, main retains actual guarded clipboard inside publicationLock -> session, with no phase/core held. A safe explicit two-stage option is: (1) original phase -> publicationLock -> session validates and reserves one copy receipt; (2) after phase release, publicationLock -> session rechecks original cancellation, foreground-first epoch/unlocked, revision, mixed registration, deadline and current code window, marks the copy attempt consumed and performs only clipboard write. Once-reserved/attempted flags prevent concurrent/reentrant copy or retry after failure. Result success and cleanup follow outside every fence. Any Request-owner permission called inside this final clipboard fence must be a dedicated bounded read of Request fields, not requestGuard.publish, session methods, storage, provider, or arbitrary EffectGuard. Alternatively the final clipboard fence can be the only copy-attempt claim, using direct context cancellation under session and bounded Request-field guard; then document that phase cancel is observed by volatile metadata rather than ordered by holding phase. Do not pretend either option is a list-summary delivery claim.

The second list/copy check rejects cancellation or window change after reservation but before actual effect. Once the final check has passed and actual Result/Binder write begins, later cancellation cannot recall it. Context.cancel/session.lock/registration changes may wait on session until the effect returns; phase.cancel stays responsive because actual effect does not hold phase. This preserves the current disclosure fence semantics but is an explicit responsiveness limitation. A window can advance immediately after a check, and a system/transport call cannot be preempted by a metadata deadline. Do not hold phase across Result/Binder to try to strengthen this guarantee.

**Retained external callback/reentry risk:** core commits own core then acquire publicationLock (`AppSecrets:1347-1353`). If an actual list Result.success invoked under publicationLock/session synchronously reenters a core-synchronized API while another worker owns core and waits publicationLock, the cycle is publicationLock -> external Result -> core vs core -> publicationLock. Removing cleanup from the callback removes known core cleanup calls, but cannot prove arbitrary Result implementations nonreentrant. Production MethodChannel.Result may be treated as transport-only disclosure only with an explicit bounded/nonreentrant assumption; JVM fake callback tests must not claim the risk disappeared. No known core reentry originates in SensitiveClipboard itself. Moving actual list Result outside all locks avoids this cycle but relaxes direct-session-lock disclosure ordering; that alternative requires an explicit product contract decision, not an implementation shortcut. No broad mutation-lock refactor belongs in this increment.

## Caveats / Not Found

- Proposed context/result APIs and read-work slot are recommendations for main-session contract review; final added main direction is phase-only read origin guard, phase -> publicationLock -> session reservation, then publicationLock -> session actual list-code/clipboard disclosure with original-state/window recheck, no phase/core, and outside-lock cleanup/copied:true callback. No implementation is present in this research artifact.
- Existing legacy management previews still use `totpPublication`/shared Bridge publication; they cannot be silently routed through a consumed-read-only receipt. Ordinary TOTP mutations, SSH typed/private/credential/trust and own-NEW-CAS continuation remain separate work.
- A pure-manifest validator requirement at read-context creation would regress provider-independent TOTP; compare captured registration only after actual SSH source is established, and preserve that fact in operation/result provenance.
- No provider preemption, Android Binder/Result completion atomicity, full-core responsiveness, production validator or complete SSH-client acceptance is established. Actual disclosure retains session blocking and potential arbitrary Result reentry risk described above. No tests/build/device/network were run in this research.
