# 父任务集成设计

## 目标与边界

本任务汇总三个已归档子任务的交付证据，核对它们之间的状态、权限和导出约定，并让 `design/` 与当前实现一致。只读检查源码；若发现需要产品代码或设备操作才能解决的缺口，记录证据并停下请求用户决定。

不在父任务中增加产品能力、改变 Root/PTY 或数据持久化策略、重新安装应用、操作开发板，或把未验收的历史建议标记为已实现。

## 子任务与集成契约

| 顺序 | 归档任务 | 集成检查 |
| --- | --- | --- |
| 1 | [可信状态与工作台基础体验](../09-25-trustworthy-state-workbench/prd.md) | 连接快照的新鲜度、部分/失败/无匹配状态可区分；设备信息权限受限不冒充真实零值；App 与 Root 状态分别表达。 |
| 2 | [只读任务与选择性导出闭环](../09-25-read-only-task-loop/prd.md) | 信息对象上下文进入只读诊断；只有已限定的三个任务进入有界历史；历史上限、清理及逐项 SAF 导出符合用户选定方案。 |
| 3 | [界面与终端可用性整理](../09-25-interface-terminal-polish/prd.md) | 统一页面层级和大屏阅读宽度；连接结构化展示继续使用同一快照；终端快捷键、PTY 生命周期、输出搜索/复制不破坏既有权限边界。 |

三项交付共同遵守 App API、Root 采集、Root PTY 和 App PTY 的边界。当前产品不依赖 Vector；归档前历史记录中出现 Vector 的部分按其原始日期解释，不作为当前架构。

## 证据规则

- 子任务 PRD、实现/检查记录和各自提交是验收结论的主证据；父任务只验证这些结论之间没有冲突。
- 当前代码解释现行实现，`design/verification.md` 解释实际构建、设备、权限和未测范围。旧 APK、旧设备状态和旧测试结果不能覆盖较新的结论。
- 设备身份保持 `TARGET-BOARD` 等项目占位符。父任务不推断设备仍在线，不复用子任务设备授权。
- P2 当前 release APK 的哈希及本地检查记录属于 P2；P1 仪器、SAF 和重启持久性结论只在 P1 的实际产物与范围内引用。

## 需要收敛的文档

- 父 PRD 使用归档后的子任务路径；检查归档移动导致的相对链接失效。
- `design/README.md`、`plan.md`、`architecture.md` 和 `changelog.md` 以当前交付为准；`opportunities.md` 保留历史建议，同时标出三个任务已完成的范围。
- `verification.md` 已有各子任务实测记录，只在链接或事实冲突时修正，不复制原始日志或设备标识。
- 父任务 `check.md` 用验收矩阵记录每项证据、结果和边界；父 PRD 勾选仅在证据核对完成后进行。

预审链接核查覆盖 17 份 Markdown 文档、93 个相对链接，共发现 8 个失效目标：父 PRD 中的三条子任务链接已在本计划修正；余下五条来自归档后 P1 任务的同级任务/验证文档路径、`design/README.md` 的 P1 链接，以及 `design/changelog.md` 的 00 归档任务链接。核查结论还确认 `09-25-read-only-task-loop` 没有单独的 `check.md`，集成记录应链接其 PRD 与实现记录中的实际结果，不新造历史检查文件。

执行时发现已归档 P0 的八项 PRD 验收框未同步勾选。用户选择先依据已保存的检查/设备记录补齐逐项验收，再继续父任务；P0 追补保留 APK 版本、模拟与实机覆盖差异及 Vector 后续移除的边界。最终检查范围为 29 份 Markdown、168 个本地相对链接，缺失目标为 0。

## 完成判断

无产品代码差异；父任务每项验收条件均能链接至有效的归档任务或验证记录；设计文档陈述准确、不扩大权限或设备结论；文档链接、任务状态与 Git 状态检查通过。若出现交付冲突、重要证据无法访问或必须超出本范围才能满足标准，则保留任务未完成并向用户说明。
