# Agent 间测试交接

用户安排其他 agent 或 session 执行测试，主 Codex 编排任务并独立审核结果。`test/codex-wont-do/` 是共享文件系统上的逻辑 `socks_dir`：`template.json` 定义测试单和协作协议，每个 `START_TIMESTAMP-MODEL_NAME-TESTS_ITEM_NAME.json` 是一个独立测试任务；它不创建网络服务，不负责发送通知。时间为任务创建批次的 UTC 起点，模型名记录创建者已知的实际精度，执行时间及执行者另记。

Codex 如何建立和分发需求、审核报告及使用结果见 [Codex 测试分发与成果使用](codex-test-management.md)。

任务单同时记录目标、源码与环境、可用资源、前置条件、测试步骤、通过标准、阻塞原因和审核重点。`queued` 表示等待领取，依赖尚未满足时不得开跑；`running` 表示已领取，`blocked` 保留具体原因，`review_pending` 表示执行方已交报告。只有独立 Codex 审核者可设置 `approved` 或 `changes_requested`；重新执行保留旧尝试和历史。报告结果 `pass`、`fail`、`blocked`、`inconclusive` 与审核结论相互独立，接受一份失败报告不会使测试或项目通过。

领取和更新使用目录内 `.locks/` 的原子目录锁，任务锁及资源锁的命名、排序、失败释放和遗留锁处理见模板。持锁者使用同目录临时文件和原子重命名写入 JSON；所有参与者都遵守共享构建与源码资源锁。锁只协调同一共享文件系统中的合作方，不验证身份，跨机器需要先提供同一一致共享目录；原始报告内容始终需要证据审查。

执行方记录开始／结束时间、执行者、环境、dirty 工作树、HEAD 及覆盖相关输入的测试前后 SHA-256 清单、实际命令和退出码、测试数量及跳过项、证据路径和摘要。HEAD 不能代表未提交变更；若源码在执行期间变化且无法证明影响范围，报告应为 `inconclusive`。测试单允许的测试夹具改动要记录 diff 和最终受测快照，不得静默修改产品行为或验收条件。

任务单中的 HEAD 和 dirty 状态记录创建时刻；如果随后只是将同一源码内容提交，执行时 HEAD 可以不同，但仍须核对固定文件、记录实际工作树及完整相关输入清单。其他变化按实际影响和验收范围处理，不能仅凭提交号推定测试输入一致。

本批 SSH 任务区分可领取项、前置实现未完成项和缺少设备授权项。较早全量 JVM／JNI 结果不等于最新源码全量通过，既有最新定向结果仍按其原证据范围保留。设备、真实账号及真实凭据不因创建任务而获得授权；仅使用受限合成资源，涉及当前未授权操作时先保持阻塞。具体任务与旧证据的关系见 [SSH 接管档案](handoff-ssh-terminal-client.md)。
