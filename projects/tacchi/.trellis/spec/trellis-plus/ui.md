## Product boundary

The user selected Kotlin native platform Views on 2026-10-26, superseding the initial Flutter + Kotlin UI choice to reduce APK size. Kotlin owns the single-page presentation and Android/settings/command/status integration. Do not introduce Flutter, Compose, React Native, WebView or a JavaScript bridge without a new explicit decision. Host enrollment, per-operation authentication and payment credentials remain in the target application's process. The configuration surface must never accept or display payment passwords, ciphertext or decryption keys.

The P0 page presents framework, host and probe status separately. Keep timestamped read snapshots, invalidate asynchronous reads on lifecycle changes, and never infer host confirmation from framework connection. Former Flutter widget tests/screenshots are historical evidence; native Activity layout/TalkBack acceptance requires appropriate native tests.

## UI acceptance before coding

Define small-phone and landscape layouts, text scaling, theme behavior, system insets, touch targets, semantics and focus/back navigation in task design. Use at least48dp touch controls, meaningful state labels and non-color status cues. Respect reduced motion; avoid decorative animation and hover-only controls. Test readable contrast rather than trusting generated accessibility labels. Native mobile coverage is required; desktop/web support is not implied.

A screenshot or successful build does not establish interaction correctness. Record screen size, scaling, fixture state, user action and final state. Separate JVM state tests, native UI test execution and TalkBack/physical-device/system-biometric evidence. Compiling an instrumentation test is not executing it. Preserve redacted failure screenshots/logs under task evidence or a documented temporary location. Never capture payment secrets or complete host View trees.
