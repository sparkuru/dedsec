# Thanox 9.6-prc UID resolver: installed APK bytecode

## Scope and provenance

On 2026-11-25 the designated `product:rk3568_firefly_aioj` board reported Android API 30, user 0, and installed `github.tornaco.android.thanos` version `9.6-prc` (`versionCode=3404474`). A read-only copy of its base APK had the same SHA-256 as the device file: `9a5ea71f300f32dc76c4107b01c269cd94508f4e0ea72674bee5c15bb21806b3`. The APK contained exactly one `classes.dex` and one `classes2.dex`; bounded extraction gave SHA-256 `9f2c584477ef39f3e17fbf88d80156b391922edb117042fc54b80ddaace55d68` and `09830789758cae00c63994ec3e58972230a7941d529b424194ccaa86d0253bca`, respectively. Both are DEX version 038. The relevant methods below occur in `classes2.dex`.

This is a static inspection of a specific installed APK copy, not recovered original source. The device reported its last package update at 2026-11-23 17:45:21 in `Asia/Shanghai`; its wall-clock/uptime observation was consistent with a later boot at approximately 17:48:13. That timing and the earlier live `tv_input` interface/version observations support investigation of this APK but do not attest the exact bytes loaded by the currently registered Binder or rule out another implementation.

## Observed service wiring

Two independent instruction listings, Android SDK Build Tools 35.0.0 `dexdump` and radare2/rabin2 6.1.6, agree on the following selected code offsets. Class names are those in the obfuscated DEX and are meaningful only for this APK hash.

- `T.serviceInstallName` at `0x26cd08` returns `tv_input`; `uj9.OooOOOo` constructs an `IThanos` implementation and, on its checked publication path, passes it to `sl9.OooO00o`, which calls `ServiceManager.addService`. The implementation `vj9` returns the familiar `I am Thanox!!!` identity string. These observations are consistent with, but do not prove the provenance of, the live Binder observed earlier.
- `uj9.<init>` creates a `zr6` package-service object and a `jb6` operations-service object, passing the same `uj9` owner to the latter. `uj9.OooOOo0` passes both objects to the `vj9` root-service constructor. The `vj9` getters at `0x4db5b8` and `0x4db5f8` create the `IOps` stub `ob6` around `jb6` and the `IPkgManager` stub `as6` around `zr6`.
- `as6.getUidForPkgName` at `0x467740` delegates the supplied `Pkg` to `zr6.getUidForPkgName`. That resolver at `0x46408c` obtains the requested user ID, selects a per-user package pool, and looks up the package name in a `ConcurrentHashMap`; missing pool or entry returns `-1`. Selected `ss6` methods populate and remove package/UID cache entries. The cache's complete lifecycle and synchronization with Android package changes were not exhaustively reviewed.

## AppOps paths

- `ob6.getPackagePermInfo` delegates to `jb6.getPackagePermInfo`, which can invoke `jb6.OooOo`. When this path reaches `0x44c530`–`0x44c53e`, it reads the owning `uj9`'s `zr6` field and invokes the same `getUidForPkgName(Pkg)` method before querying AppOps. Some conditions return early or catch an exception before reaching that lookup.
- `ob6.setMode` delegates to `jb6.setMode`, which constructs and submits a runnable whose selected switch branches reach `jb6.OooOoOO`. On a write path reaching `0x44cf88`–`0x44cf96`, that method rereads the owning `uj9`'s `zr6` field and calls the same UID method. It then calls Android `AppOpsManager.setUidMode` at `0x44cfa8` and package-specific `setMode` at `0x44cfc2`; no local negative-UID branch appears between the lookup and those calls.
- The root initially captures the `zr6` object from the same `uj9` whose reference is retained by the operations service, but operations later reread that owner's field. The inspected excerpts do not prove the field cannot change or that the objects and cached results remain identical over time. This is evidence for the named method and initial wiring in this APK, not a guarantee for every permission helper, APK version, runtime service instance, or timing scenario.
- Depending on the state, runtime-permission grant/revoke and permission-flag helpers can run before the AppOps UID lookup. Later failure may therefore leave partial effects; no transaction or rollback was established. The client-side identity checks are not atomic with the write.

## Write scheduling and waiting

Further selected bytecode shows `jb6.setMode` subscribing through `b51` and then calling `fd0.OooO00o`. That helper calls `CountDownLatch.await()` without a timeout at `0x359ec0` if the count is nonzero; the success callback counts down, while the error callback stores a throwable and counts down. After waiting, the helper converts and throws a stored error. The scheduler and callback-delivery chain was not fully inspected, so this does not prove every submitted write runs or completes, nor that every failure reaches the callback.

The bridge currently sends operations on a single background worker. If an applicable live service call were to block indefinitely, that worker could stop processing subsequent requests. No such hang was induced or observed. A timeout alone would not establish that an already issued Binder mutation was canceled, so any recovery design must account for an uncertain, possibly delayed write.

The UID-level `setUidMode` call is consistent with the previously observed phone experiment in which changing one shared-UID target affected another. It does not by itself establish the effect of every state or device. The existing conservative shared-UID write rejection and pre/post identity checks remain necessary.

## Tool limits and evidence

REA detected both DEX headers. Its isolated Ghidra provider initialized but `open_binary` rejected `classes2.dex` as an unsupported format (`target_analysis_failed`, evidence `88af0e70406b28aa4eeb`); a separate strings query failed with an unclassified broken pipe (`b1b85579306bfff82bf1`). No Ghidra decompilation is claimed. Bounded read-only fallback used the already installed Android `dexdump` and radare2 in the host execution sandbox; radare2 additionally used `-N -S -x` to disable user configuration, enable its sandbox and avoid executable mappings. No target code was executed.
