# Shared UID permission impact

## Scope and setup

On 2026-11-23, a focused continuation of the permission-boundary review used the designated `product:PLR110` device, Android API 36 and Thanox Pro `9.1-row` (`versionCode=3380725`). The three exact test package names were absent from the package list before installation. No pre-existing app was selected for a write.

Two code-free, target-SDK-35 apps, `im.majo.thanoxbridge.test.shareduida20261123` and `im.majo.thanoxbridge.test.shareduidb20261123`, each declared CAMERA and the same `android:sharedUserId`. They were signed with one temporary key. A separately signed ordinary-app probe, `im.majo.thanoxbridge.test.shareduidprobe20261123`, used the existing Thanox 9.1 IOps protocol and was hard-coded to target only app A. The installed APK hashes matched the generated files: A `667eedc9eb21e94d74db23e60fd3011f505abbbf07952a92fe0837d2290e368c`, B `40b087418194e345fa60292f17550a96ccd767ccdb4233b6e24d8865160cc961`, and probe `5f1f67a7cab577f92e911216f243e0aa28eb4ad78a8bef25b8fa32986a399d7a`.

Android user 0 assigned both targets UID 10538 and the probe UID 10539. A shell package enumeration reported two packages for UID 10538, and the two task targets were those packages. The probe required API 36, user 0, the expected target UID, the Thanox descriptors and version, and the expected CAMERA operation and permission before executing a stage. Fixture source and manifests are in `shared-uid-probe/`; temporary signing keys and built APKs are not product artifacts.

## Observation

Both targets initially reported CAMERA denied and UID AppOps mode `ignore`. The probe requested `ALLOW_FOREGROUND_ONLY` only for A. Thanox reported the requested state for A; independent Android package and AppOps reads then showed CAMERA granted and UID mode `foreground` for **both A and B**. B had not been named in the Binder write.

The probe then requested `DENY` for A. Independent reads showed CAMERA denied and UID mode `ignore` for both targets. The post-test permission flags included `USER_SET|USER_FIXED`, unlike the initial flags, and A retained an explicit package AppOps entry, so the initial metadata and entries were not exactly reconstructed. Uninstalling both disposable targets is required to remove their test state; it must not be described as exact restoration.

This establishes a shared-UID side effect for this CAMERA operation and tested device/Thanox combination. It does not demonstrate camera use, the behavior of every operation or version, or whether the service's internal UID resolvers are equivalent.

Android documents that packages can request a shared UID and that [UID-level AppOps apply to apps in that UID](https://android.googlesource.com/platform/frameworks/base/+/android-16.0.0_r1/core/java/android/app/AppOpsManager.java). [`PackageInfo.sharedUserId`](https://developer.android.com/reference/android/content/pm/PackageInfo#sharedUserId) reflects the manifest attribute. Because Android enumeration may itself be filtered, a returned package count of one is not a reliable reason to permit a write. The conservative product response is to keep packages declaring a shared user ID readable and disable their permission writes, even when another member has not been observed.

## Product boundary and remaining work

Before this continuation, `PermissionRepository` validated the selected package identity and Android/Thanox UID agreement but did not reject a shared user ID. The operation UI was presented per package, so its scope could exceed the chosen app. The native implementation now rejects the shared-user declaration before a Binder mutation and during identity rechecks, exposes the operations as read-only, and explains the restriction. This does not remove the already documented non-atomic identity checks or prove server-side resolver equivalence.

The rebuilt debug APK SHA-256 `9ed6ed87a67c43d71dde62fe4021d2d5b2b715de86a2f175b5debfddc00b0bce` matched the installed product. An explicit Android exact-package lookup opened target A without enumerating the app list. Its detail screen displayed the shared-UID explanation and showed the CAMERA operation as read-only, with no clickable control.

A separately built instrumentation APK, SHA-256 `93c4f6551166361f94c3e2321004538d1f2b2e6ee7e794e77146e0e1984dd2aa`, matched the installed test APK. Its test verified the exact package names, shared user declaration, target SDK, code-free status, expected UID and generated test-signing-certificate digest before directly calling the real `PermissionRepository.setOpMode` for A. It reported `Shared UID safety: PASS` and `INSTRUMENTATION_CODE: -1`; independent system reads after the call showed CAMERA denied and UID mode `ignore` for both targets. The test observes before/after state and does not by itself exclude a transient mutation that was later reversed; source review confirms the pre-write check.

After verification, the instrumentation APK, product debug APK, probe and both targets were uninstalled. Package-list checks including uninstalled entries found none of the exact task package prefixes, and the exact temporary device APK paths were absent. The task-owned host scratch directory, including test APKs and signing keys, was removed. The targets' effective CAMERA state was denied before uninstall; their original permission flags and default AppOps entry were not reconstructed, and uninstall removed the disposable packages' state.

The dedicated instrumentation runner was later made opt-in to avoid replacing the runner for ordinary Android tests. Offline builds confirmed that the default test APK retains `android.test.InstrumentationTestRunner` and `-PsharedUidSafetyTest=true` selects `im.majo.thanox_bridge.SharedUidSafetyInstrumentation`. The opt-in APK SHA-256 was `26744b9229f3b7194bdbc08ffe505bcfd031c8d5a200e1adebcb45332c476211`; its installed hash matched and Android listed the expected runner. A second device invocation intentionally omitted its required fixture arguments and returned `Missing or invalid expectedUid instrumentation argument`, confirming that the new runner was invoked and failed before touching a target. The full fixture PASS above used the earlier APK with the same test class and explicit runner, not this later opt-in APK. Both test and product packages were uninstalled again; package and temporary-path checks were empty.

On 2026-11-25 the opt-in runner was adapted and exercised end to end on the designated Android 11 development board, including the real repository rejection and independent post-test reads. That board run used a later APK and does not retroactively establish a full phone run for the earlier opt-in APK. See `same-root-device-20261125.md`.

For a later dedicated run, first recreate and independently verify the two disposable fixtures, their shared UID and their temporary signer; do not use existing apps. Build with `HAKO_NETWORK=none ./hako sh -c 'cd android && ./gradlew :app:assembleDebugAndroidTest -PsharedUidSafetyTest=true --no-daemon --offline'`, install the matching debug and test APKs, and invoke `adb -s <PLR110-serial> shell am instrument -w -r -e expectedUid <fixture-uid> -e fixtureSignerSha256 <fixture-certificate-sha256> im.majo.thanox_bridge.test/im.majo.thanox_bridge.SharedUidSafetyInstrumentation`. Independently check both permission states and remove the fixtures and temporary APKs afterwards.
