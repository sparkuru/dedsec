# Research: App-list access controls and the reported prompt

- Query: Could a separate app-list access control explain the user's remembered first-run prompt and the incomplete Android enumeration? Identify source evidence, a candidate read-only status query and a privacy-preserving comparison.
- Scope: the initial research used local project and archived Thanox source plus official Android documentation; the subsequent device comparison is recorded separately below.
- Date: 2026-11-23

## Findings

### Files found and code patterns

- `archive/thanox-repo/android/android_framework/base/src/main/java/github/tornaco/android/thanos/core/secure/ops/AppOpsManager.java:493` and `:550` define two distinct operations: Android `OP_QUERY_ALL_PACKAGES`, whose value is `91` in `AppProtoEnums.java:125`, and Thanox `OP_GET_INSTALLED_PACKAGES = 1000099 + 2 = 1000101`. The same class includes custom operations in `getAllOp()` at `:1205`, and describes the mode constants at `:38`.
- `archive/thanox-repo/android/android_framework/base/src/main/java/github/tornaco/android/thanos/core/secure/ops/OpsTemplate.java:108` includes the custom operation in `THANOX_TEMPLATE`. `AppOpsManager.java:1226` maps the custom operation to an array index; `archive/thanox-repo/android/app/src/main/java/github/tornaco/thanos/android/ops/model/Ops.java:73` uses that index for the label. The corresponding Chinese label is “获取已安装应用列表” at `archive/thanox-repo/android/android_framework/res/src/main/res/values-zh-rCN/app_strings.xml:742`; the Android operation has a separate “Query all packages” label at `:730`. The custom operation's description is at `:630`.
- `archive/thanox-repo/android/android_framework/patch-magisk/bridge/src/main/java/github/tornaco/android/thanox/magisk/bridge/proxy/am/AppOpsManagerProxyProvider.java:51` contains a generic legacy Android AppOps proxy: when enabled, it checks Thanox's operation mode and returns `MODE_IGNORED` for an ignored operation. This establishes a possible interception architecture in the archived source, **not** a link between package enumeration and custom operation 1000101 on this phone. The only exact references to the custom operation found under `archive/thanox-repo/android` were its definition and template; the package-enumeration hook and service implementation were not found.
- `archive/thanox-repo/android/android_framework/res/src/main/res/values-zh-rCN/app_strings.xml:996` describes legacy Thanox permission controls as separate from system controls; `:997` also describes a newer permission-management mode. This is an application description, not evidence that the legacy feature or custom op is enabled or effective on PLR110. The separate “隐藏已安装应用” string at `:1308` does not by itself establish its behavior or relationship to this issue.
- `android/app/src/main/kotlin/im/majo/thanox_bridge/PermissionRepository.kt:16` calls Android enumeration and `ThanoxCatalog.list` independently and merges the results; it does not query or interpret custom operation 1000101 before doing so. `android/app/src/main/kotlin/im/majo/thanox_bridge/ThanoxOps.kt:34` handles codes below 121 using the distinct newer `core.ops.IOps` interface. Its `PermInfo` states and the legacy interface's integer modes must not be assumed interchangeable.
- `.trellis/tasks/11-20-verify-thanox-pro-api/research/permission-device.md:81` records a same-UID, same-signer disposable probe whose Android enumeration returned only itself and omitted the task target, while exact lookup found that target and the `QUERY_ALL_PACKAGES` permission reported granted. A standard Android AppOps read reported no recorded operation and default mode. An earlier *different caller* saw 567 Android entries and its target (`:55`). These observations do not measure the custom Thanox operation, isolate the remembered prompt, prove an access denial, or establish completeness.

### Candidate status query and wire evidence

`archive/thanox-repo/android/android_framework/base/src/main/java/github/tornaco/android/thanos/core/IThanos.aidl:28` declares `getAppOpsService()` seventh. `archive/thanox-repo/android/android_framework/base/src/main/java/github/tornaco/android/thanos/core/secure/ops/IAppOpsService.aidl:7` declares `checkOperationNonCheck(int code, int uid, String packageName)` twelfth, returning an `int`. The Thanox UI uses it to load per-package operation modes at `archive/thanox-repo/android/app/src/main/java/github/tornaco/thanos/android/ops/ops/repo/PkgOpsLoader.java:28`; `AppOpsManager.java:1260` delegates the wrapper to the service.

If, and only if, the installed implementation's transaction mapping is independently verified against its Stub/Proxy for this version, the declaration-order candidate is: root transaction 7, `readException()`, `readStrongBinder()`; check child descriptor `github.tornaco.android.thanos.core.secure.ops.IAppOpsService`; child transaction 12 with its interface token, then `writeInt(1000101)`, `writeInt(ownUid)`, `writeString(ownPackage)`, and read `readException()` followed by one `int` and check for unexpected reply data. Archived source defines 0 = allowed, 1 = ignored, 2 = errored, 3 = default, 4 = foreground (`AppOpsManager.java:38`); validate the installed version rather than treating these as established device results.

**Safety and validity:** Matching a descriptor does not establish a transaction mapping. A blind raw Binder call could invoke another method if the installed AIDL differs, including a mutator; do not send it on source ordering alone. The local checkout does not establish ordinary-app authorization or server implementation, so the name and UI use suggest a status read but do not prove it cannot log, prompt, or have other side effects. Nor does any returned mode alone prove actual enforcement. Do not substitute `checkOperation` or a setter as a workaround.

### Interpretations and controlled comparison

The user's recollection is relevant first-hand evidence of a possible additional prompt, but it is uncertain which app/ROM component displayed it or which option was selected. Possible separate mechanisms include an OEM privacy controller, Thanox's custom op or a different visibility filter; no evidence here attributes the observed enumeration to any one of them. A permission marked granted by Android does not verify the settings or enforcement of those separate layers.

A suitable follow-up uses an already authorized, disposable, separately signed probe and exact disposable target, both confirmed absent before installation. On the same probe identity, UID, signature, version and user, run Android `getInstalledApplications` and `getInstalledPackages`, but persist only totals and a Boolean for the task-owned target; also compare exact target lookup and the Android permission grant. Record any task-specific prompt's wording and owner only with appropriate privacy care. If the control can be identified and the user intentionally authorizes the change, alter **only that probe's one identified control** through the appropriate user-facing prompt/settings and repeat the same observations. If the custom read interface is independently validated as safe, an optional status read may target only the probe's own package/UID; otherwise omit it. Do not enumerate or log unrelated package names, collect broad system logs, enable package-visibility logging, or use Thanox's privileged catalog to work around a possible denial.

A changed target-found result and totals after changing only the identified control would support that control influencing this probe under those conditions; unchanged results or no identifiable prompt leave the cause unresolved. A result can still be partial even after allow. Explicitly preserve the difference between a grant for the temporary probe and a grant for the product. Remove only task-installed probes/target and their task-specific temporary files; verify those exact packages are absent, without changing pre-existing app settings or claiming to restore user-level state beyond the disposable packages.

### Official external references

- Android documents [`QUERY_ALL_PACKAGES` as a normal permission](https://developer.android.com/reference/android/Manifest.permission#QUERY_ALL_PACKAGES); it is not itself a standard dangerous runtime permission. An OEM or third-party controller can have separate behavior, which remains unverified here.
- Android's [package visibility documentation](https://developer.android.com/training/package-visibility) states that visibility filtering can affect `getInstalledApplications`, and its [declarations guidance](https://developer.android.com/training/package-visibility/declaring) explains explicit package declarations and the broad permission.
- Android's [visibility testing guidance](https://developer.android.com/training/package-visibility/testing) illustrates logs naming interacting packages. Do not enable its optional `pm log-visibility` diagnostic for this privacy-limited comparison.

### Related specs

`.trellis/spec/trellis-plus/android-capabilities.md:13` requires package plus Android user/profile identity and distinguishing declared/runtime permissions, AppOps and platform controls. `.trellis/spec/trellis-plus/validation.md` and `development-principles.md` apply to controlled, traceable validation.

## Caveats / Not Found

- There is no evidence in the inspected source identifying the remembered dialog's owner, mapping the package-list call to operation 1000101, or establishing that the archived Thanox interception path is active on PLR110. The installed implementation's Binder mapping, permissions, side effects and current custom-op state remain unverified.
- During the initial source research, no operation status was read and no device experiment was run. The source findings are hypotheses and candidates for verification, not a diagnosis.

## Device comparison on 2026-11-23

On the designated `product:PLR110` (Android API 36, Thanox Pro 9.1-row), the task installed two previously absent, separately signed disposable packages for user 0. The code-free target had UID 10532 and APK SHA-256 `900a1690df97f21a6228d1f47a21c47ac99fd51b9646bf015057795b8c354d1e`; the ordinary diagnostic caller had UID 10533, target SDK 35 and declared `QUERY_ALL_PACKAGES`, without a target-specific `<queries>` entry. The target and caller signing-certificate SHA-256 digests were respectively `98d51161f14b9e036849326a8fd8ddfa90edb713555b2e6f3f80eb20260c75db` and `22ee3dd268ec599600d7a1184d54cdc85470dc201815e2528cc5c7a2b8309273`. The caller's first UI was covered by the system action bar, so it was updated with a layout-only fix using the same signing key and UID before the first button-triggered query. Android accepted the in-place update; the updated installed APK matched SHA-256 `fb36d391b900a9665f2127bc6522a8093534adbe80485b4c1d5a79687379f9a4`. Probe source and manifests are in `app-list-access-probe/`.

When the button was pressed, `checkSelfPermission(QUERY_ALL_PACKAGES)` returned 0 (granted). Both `getInstalledApplications(0)` and `getInstalledPackages(0)` returned one entry, with no null objects or missing `applicationInfo` and no match for the dedicated target UID. The tested version did not classify negative UIDs as unknown, so its false match result alone cannot rule out a redacted/invalid UID. A direct `getApplicationInfo` of that target returned UID 10532, matching the independently obtained target UID. The target has no shared UID declaration. These are per-caller observations, not a test of catalog completeness. The diagnostic only compares UIDs and counts from enumeration and performs an exact-name lookup for the task-owned target; it does not log other package names. The standard Android AppOps read for the caller's `QUERY_ALL_PACKAGES` reported no recorded operation and default mode. The device's app-info UI showed no requested runtime permissions and its permission-use page showed no records; neither establishes the state of any separate OEM or Thanox control.

After these observations, the retained probe source was corrected to count a negative UID as unknown. It was rebuilt in Docker as APK SHA-256 `a9754c83924278d25755eb92eef3632d9610398b33df4756acf9ba7cd3ebaf7f`. At the user's suggestion, the probe was uninstalled and reinstalled under user 0; Android assigned it UID 10534, and the installed APK matched that hash. The target remained UID 10532. The earlier installed APK hash and results above refer to the preceding source version and UID.

The user supplied a screenshot of an app-specific prompt asking to “Read your app list”, with Decline and Allow buttons, and reported choosing Allow for the reinstalled diagnostic. The screenshot alone does not establish the prompt provider. Its generic explanation mentioned service recommendations; this diagnostic does not provide recommendations or send the list elsewhere. After the user's choice, both Android enumeration methods returned 567 entries and matched the dedicated target UID; unknown UID counts were zero, direct target lookup matched UID 10532, and the Android normal-permission check remained granted. A second query under the same UID produced the same result. The standard Android `QUERY_ALL_PACKAGES` AppOp remained unrecorded/default.

The difference from the earlier one-entry result supports the user's hypothesis that the separate access decision affects coverage. It is not an isolated deny/allow experiment: the user made no selection on the earlier prompt, and the app was reinstalled with a different UID and a small diagnostic-code change before Allow. The owner and enforcement mechanism of the additional control remain unknown, and the product's own access choice is separate. Even 567 entries do not prove catalog completeness. The diagnostic did not call the Thanox catalog or an unverified Binder transaction; Android returned app metadata into its process in memory, but its code only inspected UIDs, displayed totals and performed an exact lookup of the task-owned target.

The probe was subsequently uninstalled for user 0. After product validation, the dedicated target and temporary product build were also uninstalled. Exact package checks reported all three absent; task-specific host fixtures and screenshots were removed.

One unscoped Activity state dump unexpectedly returned information about unrelated activities while troubleshooting the diagnostic's blank screen. A later screenshot unexpectedly captured an unrelated foreground screen after the user switched apps; the local screenshot was immediately deleted. Neither was included in this record or used to reach the conclusions above; subsequent Activity inspection was filtered to the task-owned package on the device and screenshots followed an explicit foreground check.
