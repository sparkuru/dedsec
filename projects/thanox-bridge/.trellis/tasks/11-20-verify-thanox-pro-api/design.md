# First product feature design

## Boundary

This task adds the first Flutter Android project and a Kotlin bridge for the current Android user's installed apps and their permissions. Android package visibility is used to enumerate and inspect installed packages, while the Thanox Binder is a separate authority for supported AppOps and associated runtime-permission operations. Root and cross-user changes are excluded. No server or persistent background service is introduced.

The app list identifies an app by package name and Android user ID. It uses Android package enumeration and does not silently merge a privileged Thanox catalog that might defeat a separate device app-list access choice. The UI explains that device-specific app-list access can affect coverage without claiming that a particular grant or denial occurred. If a searched package is absent from that list, including when another package partially matches or list retrieval fails, an explicit exact-package lookup uses Android's package manager and either returns one current-user app or reports it unavailable. Earlier lookups cannot replace newer search results. The list does not assert complete enumeration; any selected target is revalidated with Android before its details or writes. A detail view presents declared Android permissions and their Android-reported grant state separately from Thanox-reported AppOps. Permissions without a verified control are visible but are not represented as switchable. An unsupported or unavailable operation is explicit, as are connection, loading, empty and failure states.

## Platform contract

The Flutter side calls a small typed platform-channel interface implemented in Kotlin. Calls list apps, load one app's current details and request one explicitly selected state for one operation. The detail read captures an opaque fingerprint of package, user, UID, install/update times, version, source path and current APK signers; writes require that fingerprint and recheck it immediately before and after the Binder call. Missing identity metadata leaves the package readable but disables writes. A changed fingerprint is rejected before a write; a change detected afterwards is reported as an uncertain outcome. These checks reduce stale-target risk but cannot make package verification and the Binder write atomic. Responses include package/user identity, source authority and observed state. Android package metadata comes from `PackageManager`; Thanox operations use the installed service only after its descriptor, interface descriptor and supported version are checked. Reject malformed targets, unknown states, changed identities and unsupported calls. Do not expose a generic privileged Binder or shell interface.

Before exposing Thanox operations or writing, compare the selected Android UID against the verified Thanox per-package/user UID query; a negative, unavailable, malformed or mismatching result leaves Android information readable where possible but disables writes. Repeat the comparison immediately before and after a write, reporting a post-write failure as uncertain. The exact query has been tested on user 0 only; unverified users remain read-only for Thanox changes. These comparisons do not make the Binder write atomic or prove that the UID query and `IOps` use the same server-side resolver.

For the current upstream reference, `IThanos.getOpsManager` returns `IOps`; `IOps` exposes `getPackagePermInfo`, `opToName`, `opToPermission`, and `setMode`. `Pkg` contains package name and user ID. `PermInfo` includes the reported state and runtime/background/one-time capability indicators. The exact behavior and Binder compatibility of individual operations remain subject to dedicated-device evidence; mismatches and failed readback must be surfaced instead of reported as success. The reference's operation enumeration is bounded and may omit newer platform operations, so declared Android permissions remain visible independently.

Single writes execute only after an explicit user selection and are followed by a fresh read. The current device-proof allowlist covers CAMERA and RECORD_AUDIO foreground/ask/ignore/deny and VIBRATE allow/ignore, restricted to non-system target-SDK-35 apps with the observed operation, permission and capability fields on Android 16 + Thanox 9.1. CAMERA and RECORD_AUDIO `ALLOW_ALWAYS` are excluded because the device returned foreground-only. Other operation/state pairs remain read-only until independently verified. If an operation fails or the resulting state differs from the request, preserve and display the observed outcome. If the subsequent detail refresh cannot confirm the same identity and observed operation state, display an uncertain outcome instead of stale success. Unsupported permissions are not silently changed using Root or another authority. Native Binder work runs off the Flutter platform thread and propagates errors to the UI.

## UI and validation

Use standard Material controls with searchable, lazily built lists and separate status text rather than color alone. The app list and detail page handle loading, empty, error and service-unavailable states. Write controls remain disabled during a request and offer only states justified by the device/Thanox capability information. Follow `research/flutter-ui.md` for touch targets, accessibility, resizing and safe areas.

Initially show why the app reads the list and that the device may ask for access; start the first `listApps` call only after the user taps the read-list action (or explicitly refreshes). This lets the user be ready for a device prompt that may otherwise disappear during startup. Exact-package lookup remains available before list loading. Later refreshes remain explicit. Do not represent the action as evidence that the separate device prompt was allowed.

Tests cover channel parsing, state mapping, errors and relevant UI behavior. Run Flutter analysis/tests and a real Android build through `./hako` when dependencies are available. On `product:PLR110`, use newly created dedicated apps for any permission mutation, record original and observed states independently, restore where possible, uninstall the fixtures and verify cleanup. A source declaration, test double or non-Android preview is not evidence of real-device write behavior.
