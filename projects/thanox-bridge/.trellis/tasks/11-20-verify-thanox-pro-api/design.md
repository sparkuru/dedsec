# First product feature design

## Boundary

This task adds the first Flutter Android project and a Kotlin bridge for the current Android user's installed apps and their permissions. Android package visibility is used to enumerate and inspect installed packages, while the Thanox Binder is a separate authority for supported AppOps and associated runtime-permission operations. Root and cross-user changes are excluded. No server or persistent background service is introduced.

The app list identifies an app by package name and Android user ID. It uses Android package enumeration and does not silently merge a privileged Thanox catalog that might defeat a separate device app-list access choice. The UI explains that device-specific app-list access can affect coverage without claiming that a particular grant or denial occurred. If a searched package is absent from that list, including when another package partially matches or list retrieval fails, an explicit exact-package lookup uses Android's package manager and either returns one current-user app or reports it unavailable. Earlier lookups cannot replace newer search results. The list does not assert complete enumeration; any selected target is revalidated with Android before its details or writes. A detail view presents declared Android permissions and their Android-reported grant state separately from Thanox-reported AppOps. Permissions without a verified control are visible but are not represented as switchable. An unsupported or unavailable operation is explicit, as are connection, loading, empty and failure states.

## Platform contract

The Flutter side calls a small typed platform-channel interface implemented in Kotlin. Calls list apps, load one app's current details and request one explicitly selected state for one operation. The detail read captures an opaque fingerprint of package, user, UID, install/update times, version, source path and current APK signers; writes require that fingerprint and recheck it immediately before and after the Binder call. Missing identity metadata leaves the package readable but disables writes. A changed fingerprint is rejected before a write; a change detected afterwards is reported as an uncertain outcome. These checks reduce stale-target risk but cannot make package verification and the Binder write atomic. Responses include package/user identity, source authority and observed state. Android package metadata comes from `PackageManager`; Thanox operations use the installed service only after its descriptor, interface descriptor and supported version are checked. Reject malformed targets, unknown states, changed identities and unsupported calls. Do not expose a generic privileged Binder or shell interface.

Before exposing Thanox operations or writing, compare the selected Android UID against the verified Thanox per-package/user UID query; a negative, unavailable, malformed or mismatching result leaves Android information readable where possible but disables writes. Repeat the comparison immediately before and after a write, reporting a post-write failure as uncertain. The exact query has been tested on user 0 only; unverified users remain read-only for Thanox changes. These comparisons do not make the Binder write atomic. Static inspection of the board's 9.6-prc APK found a common named UID method on the reached AppOps paths and related initial wiring; object lifetime, cache consistency, active service provenance and other permission helpers remain unproven.

Treat a package whose Android `PackageInfo.sharedUserId` is non-null as read-only, even if no other package has been enumerated. On the previously designated phone, a single-target CAMERA write also changed another package sharing the UID; an app-list filter can conceal other members. Explain this limit in the detail view, expose no allowed write states, and enforce the same rule in the native write path before the Binder call and during its existing identity rechecks. The check is conservative and does not claim that every declared shared user ID currently has multiple members.

The board continuation adds a distinct, narrowly verified compatibility profile: Android API 30, product `rk3568_firefly_aioj`, service version `9.6`, and installed `github.tornaco.android.thanos` version name `9.6-prc` / version code `3404474`. The phone profile requires Android API 36, product `PLR110`, service version `9.1`, and installed `github.tornaco.android.thanos.pro` version name `9.1-row` / version code `3380725`; the tighter phone guard has not been physically retested. Reject missing or mismatching metadata and other combinations. Bind each verified operation allowlist to the profile returned by the checked service connection. On the board profile, CAMERA and RECORD_AUDIO are writable only when the observed flags are background=false, runtime=true and oneTime=true, with `ALLOW_ALWAYS`, `ASK`, `IGNORE` and `DENY`; the unverified foreground-only state remains unavailable. VIBRATE is writable for the observed false/false/false flags with `ALLOW_ALWAYS` and `IGNORE`. Permit only the independently tested target SDK values 30 and 35 on the board profile; keep the phone profile limited to SDK 35. For both profiles, require the verified operation name as well as its code, permission and capability flags before enabling or accepting a write. Continue requiring non-system and non-shared targets, declared permissions, identity and Thanox UID agreement. Expose specific package visibility queries for both installed Thanox packages so their versions can be checked without enumerating the app list.

For the current upstream reference, `IThanos.getOpsManager` returns `IOps`; `IOps` exposes `getPackagePermInfo`, `opToName`, `opToPermission`, and `setMode`. `Pkg` contains package name and user ID. `PermInfo` includes the reported state and runtime/background/one-time capability indicators. The exact behavior and Binder compatibility of individual operations remain subject to dedicated-device evidence; mismatches and failed readback must be surfaced instead of reported as success. The reference's operation enumeration is bounded and may omit newer platform operations, so declared Android permissions remain visible independently.

Single writes execute only after an explicit user selection and are followed by a fresh read. The phone-profile device-proof allowlist covers CAMERA and RECORD_AUDIO foreground/ask/ignore/deny and VIBRATE allow/ignore, restricted to non-system target-SDK-35 apps with the observed operation, permission and capability fields on Android 16 + Thanox 9.1. CAMERA and RECORD_AUDIO `ALLOW_ALWAYS` are excluded on that profile because the device returned foreground-only. The board profile and its distinct verified states are specified above. Other operation/state pairs remain read-only until independently verified. If an operation fails or the resulting state differs from the request, preserve and display the observed outcome. If the subsequent detail refresh cannot confirm the same identity and observed operation state, display an uncertain outcome instead of stale success. Unsupported permissions are not silently changed using Root or another authority. Native Binder work runs off the Flutter platform thread and propagates errors to the UI.

For each logical detail read or write, retain one verified root-service connection and obtain both IOps and the exact-UID query interface from that connection. Do not cache it across independent requests. Keep each child descriptor check and the existing UID rechecks around the write. A failure before the write rejects it; a Binder or identity failure after the write is attempted produces an uncertain outcome. Sharing a root connection narrows the distinct-connection boundary but does not establish stable child state, that the Binder originates from the installed APK, or that verification and mutation are atomic. No actual service replacement or UID conflict has been observed; these remaining limits require targeted review.

## Prolonged requests

Keep requests serialized through a process-scoped coordinator rather than an activity-owned executor, so recreating an activity cannot bypass a still-running request. Preserve a bounded queue for normal overlapping requests. Start a 60-second uptime response deadline when a request begins execution, not while it waits in the queue. Deduct any main-thread delay before scheduling the remaining time; a blocked main thread cannot deliver a callback and device deep sleep pauses uptime. A deadline returns one explicit error to its caller, but does not cancel or interrupt the underlying operation. Until that operation actually returns, fail queued requests without executing them and reject new requests. Discard its late result; after a normal return or ordinary handled exception, release the gate and allow a fresh user-initiated read. An unrecoverable execution error instead keeps the coordinator closed for the lifetime of the process, including when that error arrives after the deadline. Queued work belonging to a destroyed activity must not later start; detaching an activity must not be treated as cancellation of an already running Binder call.

For a timed-out write, state that the outcome is uncertain and that the write may still happen; for a timed-out read or a request rejected before execution, do not imply a write occurred. Present errors through the existing Flutter error states and avoid enabling a new mutation from stale details. Exactly one response may be delivered per request, including deadline/completion races. This is a bounded response and same-process ordering guarantee, not proof of remote cancellation or safe cross-process recovery: an already sent call may continue after activity or process death, and a later read is only a snapshot.

## UI and validation

Use standard Material controls with searchable, lazily built lists and separate status text rather than color alone. The app list and detail page handle loading, empty, error and service-unavailable states. Write controls remain disabled during a request and offer only states justified by the device/Thanox capability information. Follow `research/flutter-ui.md` for touch targets, accessibility, resizing and safe areas.

Initially show why the app reads the list and that the device may ask for access; start the first `listApps` call only after the user taps the read-list action (or explicitly refreshes). This lets the user be ready for a device prompt that may otherwise disappear during startup. Exact-package lookup remains available before list loading. Later refreshes remain explicit. Do not represent the action as evidence that the separate device prompt was allowed.

Tests cover channel parsing, state mapping, errors and relevant UI behavior. Run Flutter analysis/tests and a real Android build through `./hako` when dependencies are available. On the currently designated `product:rk3568_firefly_aioj` development board, use newly created dedicated apps for any permission mutation, record original and observed states independently, restore where possible, uninstall the fixtures and verify cleanup. The prior `product:PLR110` results are historical evidence for the phone profile. A source declaration, test double or non-Android preview is not evidence of real-device write behavior.
